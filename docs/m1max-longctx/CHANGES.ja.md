# v2.12.2-m1 / v2.12.0-m1 〜 m1.3 変更内容まとめ

- **ベースリポジトリ：** MTPLX 2.12.2（本家 `youssofal/MTPLX` の v2.12.2）。`v2.12.0-m1.3` までは 2.12.0 がベースです
- **対象：** タグ `v2.12.2-m1`（ブランチ `m1max-longctx`）。下の「変更点一覧」の M1 向けの変更はそのまま引き継いでいます
- **本家との差分：** コード、テストコード、各種ドキュメント（`docs/m1max-longctx/`）、起動・検証スクリプト

## v2.12.2-m1 での変更（2026-10-04）

### 本家 2.12.2 への追従

本家の v2.12.1 と v2.12.2 を取り込みました。
主な中身は、メモリガード（すべての要求の必要メモリを見積もり、足りなければスワップに入る前に 507 で断る）、SSD キャッシュとセッションバンクの改良、ツール呼び出しやストリームの修正などです（本家の CHANGELOG）。
m1.3 で直した「長い生成が約 1.65 万トークンで止まる不具合」は、本家も #526 として別の方法で直しました。
本家の方法（書き込む前に KV を広げ、メモリが足りなければ断る）に置き換え、M1 で使う q8 の「pages」形式の KV でも正しく広がるようにしました。

- 本家 2.12.2 との差は、この版の M1 向けのコードと、下の修正です。
- m1.3 との比較（M1 Max 64GB、Qwen3.8-27B、q8 の KV、greedy、3 ターンの会話）：生成文は 2K / 32K / 128K の 9 ターンすべてで同一でした。最初のプリフィルは 2〜3% 速く（128K で 1492 秒 → 1450 秒）、2 ターン目以降の応答開始は 0.1〜0.15 秒速く、decode は ±1% 以内でした。

### M1 の処理に合わせたメモリの見積もり

本家のメモリガードの見積もりは、本家の処理での実測にもとづいています。
M1 のこの版は処理が違うので、実測に合わせて直しました。

- **プリフィルの作業領域：** この版は M1 でプリフィルを MMA カーネルで行い、スコアの行列を作りません。2,048 行のチャンクで、見積もり 3.15 GB に対し実測は約 2.05 GB でした。M1 では本家の見積もりの 70% にしました（`MTPLX_M1_MMA_PREFILL_SCRATCH_FRACTION`、1 で本家と同じ）。
- **q8 の保存状態からの復元：** この版は q8 の保存状態を、fp16 に戻さずに q8 のページへ直接戻します。本家の見積もりは fp16 に戻してから詰め替える処理として数えていて、11.2 万トークンの会話に 19 トークンを足すだけの要求を 12.99 GB と見積もって断っていました。直した見積もりは 8.84 GB で、実測（11 万トークンの会話に 20 トークンの続き）は 7.38 GB でした。

### エージェントでの長い会話の修正（本家にもある不具合）

omp で思考オン（xhigh）の作業を続けたときに見つかった不具合です。
どれも M1 に限りません。

- **長い思考のあとで会話のキャッシュが外れる：** サーバーは、プロンプトの 25% 以上が前の会話と一致するときに同じ会話とみなします。思考が長いと（7 万トークン以上）、思考の序盤にあるトークンの区切りの違い（同じ文字列で、区切りだけが違う）が 25% を割り、別の会話と判定されて、思考の全体（約 7.8 万トークン）を読み直していました。分かれ目が前のターンで生成した部分の中にあり、同じ文字列に戻るときは、同じ会話とみなすようにしました。
- **ツール呼び出しの引数の空白：** サーバーが引数の値の前後の空白をすべて削っていました。書き込むファイルの末尾の改行や 1 行目の字下げが消え、さらにクライアントが送り返した履歴が生成と 1 文字違うため、会話の保存が見送られて、次の呼び出しで直前の思考（7.4 万トークン）を読み直していました。Qwen の書式で枠になる改行 1 つずつだけを除くようにしました（複数行の値はそのまま、1 行の値は従来どおり前後を削る）。
- **生成の途中で KV を広げられないとき：** 27B の KV はデコード中に広げますが、メモリが足りずに断られると、要求全体が 507 になり、それまでに書いた回答も失われていました。各ラウンドの手前で次のラウンドの分を確保し、断られたらその時点で止めて回答を残すようにしました（`finish_reason: length` と `memory_stop`）。
- **大きなキャッシュ外れの記録：** 1.6 万トークン以上のプロンプトで半分以上を読み直したとき、その理由（会話の判定、保存状態の一覧、直近の削除）をサーバーのログに 1 行で出します。

これらを入れた版で、omp の京都庭園の課題（思考 7.4 万トークン、12 回の呼び出し）が最後まで動きました。

## m1.3 での変更（2026-10-01）

- **長い生成が約 1.65 万トークンで止まる不具合を修正しました。** 本家にも同じ不具合があり、M1 に限らない修正です。
  - サーバーは生成用の KV キャッシュを最初に最大 16,384 トークン分だけ確保し、足りなくなったら増やす設計です。ところが compiled verify が使う形の KV キャッシュには容量を増やす処理がなく、確保した分を使い切ると容量の外に書き込んで値が壊れ、出力が NaN になってエラーで止まっていました。
  - thinking オンで長く考えさせると必ず起きていました（Qwen3.8-27B、xhigh で約 16,530 トークン目）。compiled verify の文脈の上限を下げても直らず、最初から全量を確保する設定（`MTPLX_DYNAMIC_PAGED_KV_MAX_INITIAL_NEW_TOKENS=unlimited`）では起きないことで原因を確定しました。
  - 修正：compiled verify の KV キャッシュにも容量を増やす処理を足し、足りなくなる前に増やすようにしました（1.5 倍か必要量の大きいほう）。17,500 トークンの再現手順と、thinking オンで最大 5.7 万トークンを生成する課題がすべて最後まで動き、速度は変わりませんでした。
  - 修正前の版での回避策は `MTPLX_DYNAMIC_PAGED_KV_MAX_INITIAL_NEW_TOKENS=unlimited` です（要求された生成量の KV を最初に確保するので、メモリを少し多く使います）。

## m1.2 での変更（2026-09-30）

- **SSD キャッシュ（`--ssd-session-cache on`）から再開するときの不具合を修正しました。** 本家にも同じ不具合があり、M1 に限らない修正です。
  - サーバーを再起動したあと、別の会話と共通する先頭部分（エージェントのシステムプロンプトなど）を SSD から再開するとき、一致した長さを 256 トークン単位に切り下げた位置を再開位置として使っていました。GatedDeltaNet を含むモデル（Qwen3.5 / 3.6 / 3.8、Flash-Next）では、その手前の保存位置まで戻って読み直していました。
  - omp（システムプロンプト約 1.9 万トークン）では、保存位置 19,337 に対して 18,432 から再開し、約 1,000 トークンを読み直していました。1 ターン目の TTFT は 10.7 秒 → 3.4 秒になりました。
  - サーバーが動いている間のメモリ上のキャッシュは別の処理なので、影響はありません。公開ベンチ（SSD キャッシュ off）の数値も変わりません。

## m1.1 での変更（2026-09-29）

- **#9 の Metal コマンドバッファの拡大を既定で無効にしました。** decode は速くなりますが（+6〜7%）、MLX のコマンドバッファのメモリ上限を上げると prefill が遅くなります。
  - 8K のコールド prefill：MLX 既定 54.7 秒に対し、上限 150 / 500 / 1,000 MB で 59.6 / 65.1 / 65.7 秒。
  - decode の得は 300 MB 以上で初めて出るため、両立する値はありませんでした。毎層の確定、非同期の確定、MLX キャッシュ 4 GiB でも prefill の損は消えませんでした。
  - マシンが使用中・電力制限のときは損が 8K〜32K で +13〜21% まで広がり、decode の得は 0〜2% に縮みました（アイドル時は +2〜5%）。
  - 長い文脈では時間の大半が prefill なので、既定では MLX の設定のままにします。`MTPLX_MLX_COMMAND_BUFFER_MB=1000` で m1 と同じ挙動（150 ops、4 層ごとの確定を含む）に戻せます。
- 公開ベンチの 2K〜128K の表は `v2.12.0-m1` での計測です。m1.1 の decode はそれより 6〜7% 低く、prefill は本家と同じになります（下の「m1.1 の確認」）。

### m1.1 の確認（2026-09-29 午後、同じマシン状態で交互に計測）

| | 8K コールド prefill | 32K コールド prefill | decode（2K / 32K 会話、3 ターン平均） |
|---|---|---|---|
| 本家 `1de2b1c` | 54.3 秒 | 247.7 秒 | — |
| m1（`v2.12.0-m1`） | 67.1 秒 | 298.9〜308.6 秒 | 31.8 / 27.0 tok/s（公開ベンチ、夜間） |
| **m1.1** | **54.5 秒** | **252.7 秒** | 29.3 / 24.8 tok/s |

- 2K / 32K の 3 ターン会話の生成文は、6 ターンすべて m1 と同一でした（greedy）。
- この時間帯はマシンが電力制限気味で、m1 の prefill の損が大きく出ています（アイドル時の損は +2〜5%）。

## 前提条件・適用範囲

- **M1 シリーズの Mac のみ適用：**
  チップ名が「Apple M1」で始まる環境（M1 / Pro / Max / Ultra）でのみ、本ブランチのチューニング（後述の既定値）が有効になります。M2 以降の Mac では本家 2.12.2 と同じ挙動になります（v2.12.2-m1 の「エージェントでの長い会話の修正」はすべての Mac に効きます）。
- **最適化の一括無効化：**
  環境変数 `MTPLX_M1_LONG_CONTEXT=0` を指定して起動すると、M1 向けの既定値をすべて無効化し、本家の挙動に戻せます（#3 と v2.12.2-m1 の不具合修正はコードの修正のため、そのまま残ります）。
- **検証済み環境：**
  動作確認は **M1 Max 64GB（macOS 26）＋ Qwen3.8-27B（FP16 版）** のみで実施しています。

## 総合ベンチマーク結果

- **測定環境：** M1 Max 64GB、Qwen3.8-27B、8-bit KV、greedy デコード、3 ターン会話、各ターン最大 256 トークン（[apple-silicon-llm-bench](https://github.com/shunya1810/apple-silicon-llm-bench)）
- **比較対象：** 本家コミット `1de2b1c`（v2.12.0 ＋ README 更新 1 コミット）。起動オプションは両者で同一で、違いは読み込むコード（`PYTHONPATH`）だけです。「本家 + env」は、同じ本家のコードに上表の「できる」の環境変数をすべて与えたものです。
- **計測日：** 本家と本家 + env は 2026-09-29 に同じセッションで交互に計測しました。本ビルド（タグ `v2.12.0-m1.2`）は 2026-09-30 に同じ計画で単独で計測しました（事前に 2K の確認でマシンの状態が同じことを確かめています）。
- decode は 3 ターンの平均（各ターンは 2 ラウンドの中央値。128K は 1 回）です。

| コンテキスト長 | 本家 decode | 本家 + env decode | 本ビルド decode | 本家 3 ターン総所要時間 | 本ビルド 3 ターン総所要時間 |
|---|---|---|---|---|---|
| **2K** | 23.6 tok/s | 27.2 tok/s | **29.3 tok/s** | 41.8 秒 | **36.0 秒** |
| **32K** | 14.0 tok/s | 15.3 tok/s | **25.5 tok/s** | 5.0 分 | **4.6 分** |
| **64K** | 8.7 tok/s | 7.8 tok/s | **23.4 tok/s** | 11.3 分 | **10.1 分** |
| **128K** | 5.0 tok/s | 4.6 tok/s | **19.0 tok/s** | 30.6 分 | **24.9 分** |

- `v2.12.0-m1`（2026-09-29 に本家と同じセッションで計測）は、decode が 31.8 / 27.0 / 24.3 / 19.6 tok/s、3 ターン総所要時間が 35.2 秒 / 4.7 分 / 10.9 分 / 25.3 分でした。m1.2 は decode が 3〜9% 低い代わりに、prompt の読み込みが速くなっています（「m1.1 での変更」）。
- サンプリング（temperature 1.0、top-p 0.95、top-k 20、最大 512 トークン）では、本ビルドが 2K / 32K / 64K で 27.5 / 25.2 / 23.8 tok/s、本家が 23.2 / 14.2 / 8.9 tok/s、本家 + env が 26.4 / 14.2 / 8.2 tok/s、Splash 1.1.0-m1 が 32.7 / 25.8 / 22.0 tok/s でした。
- Splash 1.1.0-m1 との比較：decode は 64K まで Splash が速い（2K〜8K で 13%、32K〜64K で 3〜6%。128K は本ビルドが 2% 速い）一方、3 ターン総所要時間は本ビルドが 2K〜128K で 5〜15% 短いです。短いプロンプト・推論ありの条件では、Splash の decode が 29% 速く、1 トークンあたりのエネルギーも約 3 分の 2 です。

> **読み方の注意：**
> - 総所要時間の差が decode ほど大きくないのは、1 ターン目のコールド prefill（64K で約 10 分）が時間の大半を占めるためです。本ビルドの prefill は 2K〜8K で本家と同じ、32K で 2.5% 遅く、64K で 4%、128K で 14% 速いです。
> - 各ターンの生成が 256 トークンと短い条件です。生成が長い使い方では decode の差が大きく効きます。
> - ピークメモリは本ビルドの方が少ないですが（128K で 43.5 GB 対 52.4 GB）、Splash（22〜26 GB）よりはかなり多いです。

1. **非公式ビルド：** MTPLX 公式プロジェクトとは無関係で、サポートや動作保証はありません。
2. **検証環境の限定：** 動作確認は M1 Max 64GB かつ Qwen3.8-27B のみです。他の M1 モデル、小容量メモリ機（16〜32GB）、他のモデルでの動作は未検証です。
3. **AI 支援による開発：** 変更コードは AI（Claude）の支援を受けて作成しました。
4. **アップストリーム追従：** 本ビルドは 2.12.0 をベースとしており、将来の本家アップデートへの追従は保証しません。
5. **元に戻す方法：** 不具合が生じた場合は、環境変数 `MTPLX_M1_LONG_CONTEXT=0` を指定するか、MTPLX アプリを通常どおり起動すれば、本家の挙動に戻せます。
