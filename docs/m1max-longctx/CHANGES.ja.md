## v2.12.3-m1.20 での変更（2026-11-22）

Inkling-2-Mini の会話の 2 ターン目以降で、sliding window の位置がずれていた不具合を直しました。ほかのモデルの経路は変わりません。ネイティブ拡張は m1.12 から変わっていないので、作り直す必要はありません。

- **復元した会話の sliding window。** サーバーは保存した会話を復元するとき、新しく作ったキャッシュに中身を戻しますが、位置などの付帯情報（meta state）は戻しません。Inkling の sliding window のキャッシュ（48 回の層の通過のうち 40 回、窓は 1,024 トークン）は、位置と書き込み位置をこの付帯情報にしか持ちません。そのため復元のたびに 0 に戻り、2 ターン目以降は窓のマスクと相対位置のバイアスがずれた状態で計算されていました。応答はそれらしく見えるので、気づきにくい不具合でした。Inkling のキャッシュでは付帯情報も必ず戻すようにしました（`InklingVisitCache.mtplx_restore_meta_state`、`mtplx/cache_state.py` の `restore_cache`）。ほかのモデルのキャッシュはこの印を持たないので、動きは変わりません。
- **確認。** 同じ 6K トークンのプロンプトを temperature 0 で 2 回送り、2 回目は保存した会話から復元しました。m1.19 では 1 回目が 863 トークン、2 回目が 590 トークンで、答えも違いました。m1.20 では両方とも 863 トークンで、同じ文章になりました。2 ターンの日本語の会話では、2 ターン目が 5,073 トークンを復元し、0.85 秒で答え始めました。

**テスト。** 保存と復元に関わるテスト（14 ファイル）で、失敗は m1.18 からある 2 件だけです。サーバーと同じ条件（付帯情報を戻さない復元）で、復元したキャッシュが元と同じ出力を出すことを確かめるテストを追加しました。

## v2.12.3-m1.19 での変更（2026-11-22）

Thinking Machines の Inkling-2-Mini（公式の重み `thinkingmachines/Inkling-2-Mini`、NVFP4 / MXFP8）が動くようになりました。MTP なしの自己回帰（AR）で動きます。ほかのモデルの経路は変わりません（変更はすべて Inkling の `model_type`、reasoning parser、モデル側の印で切り替わります）。ネイティブ拡張は m1.12 から変わっていないので、作り直す必要はありません。

- **読み込み。** 24 層のうち 6〜17 層を 3 周する構造（層の通過は 48 回）、expert 128 個から 8 個、相対位置のバイアスと sink を持つ attention、depth attention、message gate、short conv を、このリポジトリ内のモデル（`mtplx/models/inkling2_loop.py`、mlx-lm PR #2086 の文章部分の移植）で動かします。公式の重みはそのまま読みます。expert は NVFP4（外側の倍率つき）で、20〜23 層は MXFP8 です。BF16 の射影・埋め込み・出力層は、読み込み時に 8bit の affine にします。M1 では bf16 を fp16 に変換して動かします（`MTPLX_M1_FP16_CAST`、Inkling も既定でオン）。perplexity は bf16 のままの計算と同じです（英語 / 日本語 / コード / エージェントのログで 6.593 / 10.320 / 2.157 / 1.791 → 6.599 / 10.285 / 2.165 / 1.788）。
- **サーバー。** Inkling 用の AR の経路（`inkling2_ar`）を足しました。sampling の既定は temperature 1.0 / top_p 1.0 / top_k なし、思考の深さ（reasoning effort）は low / medium / high / xhigh で既定は high です。Inkling 独自のメッセージのチャンネル（思考、本文、ツール呼び出し）を、`reasoning_content` と `tool_calls` に変換します（`inkling2` の reasoning parser）。ツールの呼び出しと結果は、平文にせずテンプレートのまま渡します。セッションの保存は途中の境界を作らない設定にし（以前は境界ごとに全 visit の KV を複製し、5.3K トークンで 12.8 GB を保存していました）、メモリの見積もりは 1 トークンあたり 32,768 B（大域 attention の 8 回の通過の分）にしました。
- **forge。** Inkling 用の AR だけの経路を足しました。変換はせずに重みを hardlink で置き、AR で動作を確かめ、`ar_only` の印を付けます。`~/.mtplx/models` に作れば、アプリのモデル一覧に出ます。`mtplx tune` には対応していません。
- **decode。** 1 トークンの decode を、KV キャッシュの前後 2 つの compiled な関数で動かします。attention の前後の行の処理、message gate、short conv、NVFP4 / MXFP8 の expert（gate/up と SwiGLU、down と重み付きの和）を、それぞれ 1 つの kernel にしました。MLX の command buffer の上限（150 ops / 1000 MB）を Inkling の起動時の環境に入れます。さらに AR の生成ループで、次のトークンを GPU 上で引き、CPU が読む前に次の forward を投入します（`MTPLX_AR_PIPELINE`、Inkling では既定でオン、`=0` で切れます）。Inkling は 1 トークンの組み立てと投入に CPU を約 16 ms 使うので、これを GPU の計算と重ねます。サーバーの decode は 37 → 48 tok/s（2K）になりました。
- **prefill。** expert の行列積を、expert ごとにタイルをそろえて計算します（`mtplx/kernels/inkling2_seg_gemm.py`）。MLX の steel の BlockMMA と量子化ローダーを使い、`gather_qmm` とビット単位で一致したまま、5.3 → 6.4 TFLOPS になりました（+13%）。相対バイアス付きの attention は、MLX の steel attention の本体にマスクとバイアスと行ごとの sink を入れたもの（`mtplx/kernels/inkling2_steel_attn.py`）に替えました（4.1〜4.4 → 5.4〜6.1 TFLOPS）。expert の前後の並べ替えと重み付きの和、message gate も kernel にしました。切り替え: `MTPLX_INKLING2_SEG_GEMM=0`、`MTPLX_INKLING2_STEEL_ATTENTION=0`、`MTPLX_INKLING2_PREFILL_MOE=0`、`MTPLX_INKLING2_GATE_COMPILE=0`。
- **組み込んでいないもの。** 同梱の DSpark の draft（`mtp.safetensors`）は移植しました（`mtplx/models/inkling2_dspark.py`、`mtplx/models/inkling2_spec.py`）。ただ、M1 Max では投機的デコードが AR より遅いので、生成にはつないでいません。8 トークンの検証に 72 ms かかり（1 トークンは 18 ms）、受理は 1 回あたり平均 3.13 トークンでした。数トークンの検証を速くする経路（compiled、少数行の attention、expert を 1 回ずつ読む MoE）は入っています。

大域 attention は長さに比例して重くなるので、prefill と decode は長いほど遅くなります。1 トークンあたりの KV は 32 KB（大域の 8 回の通過の分。sliding window の 40 回の通過は 1,024 トークンで頭打ち）で、ほかの作業領域を含めると実測で約 41 KB ずつ増えます。1M（104 万トークン）は、fp16 の KV では 64 GB の Mac に収まりません。メモリの番人は受け付け時に約 80 GiB と見積もって拒否し、`--allow-swap` と `MTPLX_PREFILL_ADMISSION_SHED=0` で通しても、prefill の終盤で GPU のメモリを確保できずに止まります（スワップには逃げません）。64 GB の Mac で確かめた最長は 52 万トークンです。

**動作の確認。** 日本語の 3 ターンの会話、思考の深さ 4 段階、思考なし、思考の途中での打ち切り、3.2 万トークンの中の 1 行を答える課題、複数のツールの同時呼び出しで、正しく動きました。OpenCode でのエージェントの課題（15 分の制限）では、バグ修正と型注釈は effort high で合格し、多角形の物理シミュレーションは effort medium で合格しました（high では 2 万トークン以上考えて時間切れ）。2.4 万トークンの文書を読んでまとめる課題は、英語版は満点のレポートを書きましたが、日本語版は思考が長く時間切れでした。

**既知の制限。** 計測は M1 Max 64 GB の 1 台だけです。KV の 8bit 化（`--paged-kv-quantization q8`）には対応しておらず、指定しても fp16 に戻ります。思考の深さの既定（high）では、難しいエージェントの作業で長く考えます。

**テスト。** 失敗は m1.18 と同じ 84 件で、増減はありません。Inkling の読み込み（公式の形式の重み）、1 トークンの decode と数行の forward、fp16 の kernel、prefill の expert の GEMM と attention、DSpark、AR の pipeline のテストを追加しました。

## v2.12.3-m1.18 での変更（2026-11-19）

Qwen3.8-Flash-Next（Unsloth UD-Q2_0）の長い文脈が速くなり、25.6 万トークンまで動くようになりました。KV の既定が int8 になります。ほかのモデルの経路は変わりません。ネイティブ拡張は m1.12 から変わっていないので、作り直す必要はありません。

- **KV を int8 で持ちます（Flash-Next の既定）。** 1 トークン・1 ヘッドごとの float16 のスケール付きの int8 で、1 トークンあたり約 24 KB が約 12 KB になります。`--paged-kv-quantization` の既定（auto）と `q8` で有効になり、`off`（または `MTPLX_QSA_KV_Q8=0`）で fp16 に戻ります。decode（`qsa_flash_skip_q8`）と、verify と prefill の attention（`qsa_rows_mma` の int8 版）が int8 を直接読みます。draft の頭の 1 層は fp16 のままです（`MTPLX_QSA_KV_Q8_DRAFT=1` で int8 にできます）。セッションの保存と復元は fp16 の形のままなので、会話の再利用の動きは変わりません。メモリの見積もり（`memory_plan`）も int8 の大きさで計算します。m1.17 では 16 万トークンを超えると Unsloth のファイルで収まらなかったので、これが一番大きな変更です。
- **prefill の attention を rows-MMA の kernel に移しました。** 選んだ約 2,050 トークンから 1 行ずつ読む verify 用の kernel（m1.17）を、4,096 行の prefill に使います。ネイティブの Steel の kernel より 1 層・1 chunk で約半分の時間です（32K / 64K / 128K で 103 / 109 / 111 ms から 53 / 55 / 57 ms、int8 では 67 / 67 / 69 ms）。int8 の KV では既定でこの kernel を使い、fp16 の KV では `MTPLX_QSA_PREFILL_ROWS_MMA=1` で有効にできます（既定はオフ）。
- **選択（indexer）のスコア計算を 1 つの kernel にしました**（`qsa_indexer_prefill_scores_simd`）。relu とヘッドの和までを simdgroup の行列積の中で行い、ヘッドごとの float32 の面を作りません。3.2 万トークン以上の履歴の prefill で、選ばれるブロックは同じです（ISTA のパックで 12.8 万トークンの prefill が 373 → 404 tok/s）。`MTPLX_QSA_PREFILL_SIMD_SCORES=0` で元に戻ります。
- **長い prompt の prefill。** KV が小さい間は広い幅（最大 4,096 行）で進め、幅の候補を 4,096 / 2,048 / 1,024 / 512 にしました。13.1 万トークン以上では prefill の間だけ decode 用の 8bit のパックを手放し、20 万トークン以上では途中の状態の保存を省き、QSA のバッファを 1 回だけ確保します。メモリの足りない 25.6 万トークンまでを完走するための変更です。
- **prefill の expert。** 重み付きの和と silu×up と並べ替えを kernel にし（1 層あたり数 %）、タイルを 2 つの大きさ（32 行と 16 行）にして端のタイルの無駄を減らしました。n-gram の大きな cold の行は `F_RDADVISE` で先読みします（macOS）。n-gram のプロセス内キャッシュは 256 MB が既定です。
- **ISTA の Q2_0 のパック。** expert を GGUF のブロックのまま持つようにしました（メモリ −3.3〜3.6 GB、decode は同じ）。Unsloth のファイルは元からブロックで持っていました。
- **decode と verify。** 1 行の decode は、必要なブロックだけ読む sparse な attention が M1 の Flash-Next で既定になりました。hyper-connection の読みと compiled の decode は 8 行まで速い経路を使います。
- **効果がなかったので既定オフのもの（残してあります）。** `MTPLX_QSA_DECODE_SCORES=1` と `MTPLX_QSA_TOPK_KERNEL=1`（decode / verify の選択を融合した kernel と radix の top-k。12 層をつないだ測定では速いが、12.8 万トークンの実際の verify では 53.7 → 55.0 ms と遅い）。compiled の固定バンク verify（`MTPLX_QWEN4_FIXED_M4_VERIFY=1`、8K で 50.2 → 54.4 ms と遅い）。DFlash 2 の draft（`mtplx/dflash2.py`、モジュールのみで組み込んでいません。受理は増えますが draft の時間で相殺されます）。

**速さ（Unsloth の UD-Q2_0、M1 Max 64 GB、同じ日に m1.17 と交互に 2 ラウンド、コードと日本語の文章）**

8K の decode は、この 2 つの文章で 1 回に受理するトークンが少なく（3.11 → 3.00、2.75 → 2.49）、1 round の時間（64 ms）は同じでした。4 種類の 8K のプロンプト（コード / 日本語 / 英語 / エージェントのログ）を貪欲で 300 トークン出して比べると、1 round あたりのトークン数は fp16 の KV で 2.73 / 2.17 / 2.33 / 2.63（平均 2.47）、int8 の KV で 2.75 / 2.10 / 2.33 / 2.75（平均 2.48）で、体系的な差はありません。文章ごとのばらつきです。

**精度。** perplexity を対にして比べました（英語 / 日本語 / コード / エージェントのログ、各 4 窓）。Unsloth で m1.17 → m1.18 の差は +0.0003 / −0.0018 / +0.0009 / −0.0021（すべて標準誤差の 1.1 倍以内）。int8 の KV は、3.2 万トークンの履歴から 1,024 トークンを 4 行の verify で流した NLL の差が −0.00002（標準誤差 0.003）と −0.0016（0.005）でした。

**テスト。** 失敗は m1.17 と同じ 84 件で、増減はありません。int8 の KV、rows-MMA、融合したスコアの kernel、radix の top-k などのテストを追加しました。

## v2.12.3-m1.17 での変更（2026-11-16）

Qwen3.8-Flash-Next（Unsloth UD-Q2_0）の decode と prefill を速くしました。日本語の decode は思考ありで 1.4〜1.6 倍になります。長い匿名の会話で 2 回目以降が毎回 cold になる問題も直しました。ほかのモデルの経路は、セッションの保持の変更（下の「長い匿名の会話」）を除いて変わりません。ネイティブ拡張は m1.12 から変わっていないので、作り直す必要はありません。

- **日本語の draft。** Flash-Next の FR-Spec の draft は、本家の qwen4 の設定で `builtin:qwen38-code-64k`（コードの頻度順 64K 語彙）に固定されていて、M1 の既定の日本語入りの語彙（`qwen38-code64k-ja`、103,887 行）が届いていませんでした。コードの語彙は日本語の文章のトークンを 78〜84% しか含まず、日本語では最初の draft が 35% しか当たっていませんでした。M1 では日本語入りの語彙を使います。K20 prescatter の draft 経路が 64K 行の表しか受け付けなかったので、同じく行順に並んだ 103,887 行の表も受け付けるようにしました（その幅での等価性のテストを追加）。英語の decode は draft の時間が 1 round あたり約 1.3 ms 増えますが、ベンチではほぼ同じでした。
- **verify の QSA attention を、行ごとのトークンの一覧から直接読むようにしました**（`mtplx/kernels/qsa_rows_mma.py`）。これまでの verify（4 行）は、1.6 万トークン未満では全文脈を dense な mask 付きの SDPA で、それ以上では行ごとに選んだ K/V を別の配列に集めてから小さな行列積で計算していて、どちらも 1 層あたり約 1 ms かかっていました。新しい kernel は、行が選んだ 2,304 トークンの K/V を cache から simdgroup の行列積で直接読み、1 層 0.10〜0.17 ms です（8K / 20K / 60K で 768 / 990 / 920 µs から 102 / 170 / 135 µs）。fp32 で計算した参照との差は既存の経路より小さく（3.0e-5 と 4.1〜4.5e-5）、選ぶトークンは同じです。rows-gather はすべての文脈で使い、選択の予算以下（全トークンが見える）の verify も同じ kernel に通します。`MTPLX_QSA_ROWS_MMA=0` で元に戻ります。fixed-M4 の compiled verify を使う構成（M1 のパックは使いません）では、eager と bit を合わせるため既定でオフです。
- **prefill の routed expert を、MLX の量子化行列積の tile で計算するようにしました**（`mtplx/kernels/moe_gguf_qmm.py`）。m1.16 の expert ごとの行列積は、2,048 トークンの chunk で 1 層 55 ms（ISTA の Q2_0 は M1 の seg gather で 40 ms）でした。差は dequant ではなく行列積の組み方にあったので、`moe_seg_gather_m1` と同じく MLX の `qmm_t` の tile 本体（steel の BlockMMA）を expert ごとの tile で回し、重みを読む部分だけを GGUF の block の展開に差し替えました。gate と up は 2N 行の 1 つの射影として計算します。1 層あたり、2,048 トークンで 53.3 / 52.1 / 54.7 → 46.8 / 42.1 / 46.8 ms（IQ2_S+Q2_0 / IQ2_XXS+Q2_0 / IQ2_S+IQ4_NL）、1,024 トークンで 36.1 → 31.5、512 で 25.8 → 22.6、128 で 18.0 → 15.8 ms です。perplexity は 6.769 / 20.24 / 2.470 / 1.940 → 6.761 / 20.28 / 2.470 / 1.943（英語 / 日本語 / コード / エージェントのログ）。`MTPLX_GGUF_QMM=0` で元に戻ります。
- **hyper-connection の読み。** prefill の融合 kernel（norm と sigmoid の mix）が bf16 専用で、fp16 で動く M1 のパックでは eager の計算になっていました。fp16 も受け付けるようにしました（読み込み時の自己検査で bit が一致することを確認）。decode / verify の 8bit の kernel は、x と mix の読み方を変えて 1 回の読みが 1 行で 47 → 34 µs、4 行で 74 → 68 µs になりました。
- **短い prompt の prefill の attention。** 最初の約 2K トークン（QSA の選択が因果的な全体になる範囲）の chunk は、MLX の head dim 256 の SDPA（mask 付き、融合されない経路）から、このフォークの MMA の prefill kernel（`sdpa_gqa_mma_prefill`）に移しました。2,048 トークンの chunk で 5.57 → 5.52 秒です。
- **長い匿名の会話。** セッション ID もコーディングエージェントのツールもないリクエストは、会話の状態をコピー（snapshot）でしか保存しませんでした。snapshot が 1 セッションあたりの上限を超えると保存自体が見送られ、同じ文脈への 2 回目以降が毎回 cold になっていました（Flash-Next、131K トークンで snapshot 5.08 GB に対し上限 3.6 GB、2 回目も 423 秒）。3.2 万トークン以上の prompt は、明示的なセッションやエージェントと同じく live な cache を保持するようにしました（`MTPLX_SESSIONBANK_LIVE_REF_MIN_PROMPT_TOKENS`、既定 32768、0 でオフ）。短い使い捨ての prompt はこれまでどおりです。設定なしで 128K の課題を流し直すと、2 回目以降の質問は 131,116 トークンを cache から戻して 0.59〜1.0 秒で始まりました（修正前は 423 秒）。
- **Flash-Next の KV は fp16 です（訂正）。** m1.16 の文書とリリース文は Flash-Next の計測を「8bit の KV」と書いていましたが、Flash-Next の QSA の attention には量子化した KV の経路がなく、本家の設定で `q8` を指定しても fp16 に戻ります（サーバーのログに「paged KV quantization 'q8' is not supported for this model … downgrading to off」と出ます）。計測はすべて fp16 の KV でした。
- **Neural Engine（試験的、既定オフ）。** `MTPLX_ANE_PREFILL_QWEN4_GDN=1` で、GDN の入力射影（2560 → 16480）の後ろ 8,192 行を Neural Engine が、残りを GPU が同時に計算します（Qwen3.5 系の `ane_prefill.install_gdn` と同じ分け方。A3B のように chunk を半分に割ると expert を 2 回読むことになり、Flash-Next では 1,024 トークン 2 回が 63 ms、2,048 トークン 1 回が 47 ms と損が大きいため）。2,048 トークンの chunk は 5.57 → 5.26 秒（−5%）、perplexity は同じでした。ただしサーバーは Flash-Next を 4,096 トークンの chunk で prefill し、そこでは 10.68 / 10.49 → 10.42 / 10.57 秒と測定のばらつきの範囲だったので、既定ではオフです。

## v2.12.3-m1.16 での変更（2026-11-16）

Qwen3.8-Flash-Next を、Unsloth の UD-Q2_0 の GGUF で動かせるようにしました（64 GB の Mac 向け）。ISTA の Q2_0 の GGUF より perplexity がずっと低く、こちらを勧めます。ほかのモデルの経路は変わりません。ネイティブ拡張は m1.12 から変わっていないので、作り直す必要はありません。

- **Unsloth の GGUF の expert を、block のまま読むようにしました**（`mtplx/kernels/moe_gguf_iq.py`、`qwen4_exp.GGUFMixedSwitchGLU`）。Unsloth は層ごとに、routed の expert の gate / up を IQ2_XXS か IQ2_S、down を Q2_0 か IQ4_NL で量子化しています。どれも MLX の affine の格子では表せないので、読み込み時に block の scale（fp16）と本体（uint32）に分けるだけで、そのまま kernel で読みます。
  - decode と verify（1〜8 行）: gate / up は 2 つの kernel で計算します。grid の値と符号を half8 の表にして、8 重みを XOR 1 回で展開します。down は、重み付きの和と shared expert の足し込みまで 1 つの kernel で計算します。
  - prefill: expert ごとに token をまとめ、重みの tile を threadgroup のメモリに展開して simdgroup の行列積で計算します。次の K step の重みと activation を register に先読みし、expert の平均の token 数で tile を 16 / 32 token に切り替えます。

- **dense の重みも Unsloth の GGUF から変換します。** ISTA の GGUF は dense も低精度で（shared expert が Q2_0、attention や ssm_out が Q3_K / IQ4_XS / Q4_K）、Unsloth は Q5_K〜Q8_0 です。どちらも 8bit に量子化し直すので、メモリは増えません。`scripts/convert_flashnext_ista_gguf.py` は、expert の型を見て ISTA（`"format": "Q2_0"`）と Unsloth（`"format": "mixed"`）を書き分けます。
- **準備のスクリプト `scripts/setup_flashnext_unsloth.py`。** GGUF（3 分割、70.5 GB、途中から再開できます）と、Youssofal の Optimized-Speed パックの設定・tokenizer・MTP ヘッドをダウンロードし、変換します（CPU で数分）。使い方は [USAGE.ja.md](USAGE.ja.md#qwen38-flash-nextunsloth-ud-q2_0) にあります。この Mac で最初から通して実行し、できたフォルダが計測に使ったものとバイト単位で同じことを確かめました（GGUF の 3 ファイルも Hugging Face の SHA-256 と一致）。
- **パックが MTP の深さの方針を `mtplx_runtime.json` で宣言できるようにしました**（`adaptive_policy_default`、`adaptive_start_depth_default`。明示したフラグが優先）。Flash-Next はこれまで、深さ 3 だけ compile 済みの verify があるという理由で、どの方針も深さ 3 に固定していました。M1 のパックはその verify を切っているので、固定はしないようにしました。ただし変換したパックの既定は固定の深さ 3 のままです。streak（深さ 3 から始めて、外れが続くと浅くする）は思考なしの短い日本語の答えでは速い（27.9 vs 24.4 tok/s）ものの、思考ありでは遅かったためです（llm-bench の b3、エージェント 2K で 36.0 vs 42.8 tok/s、2 round とも同じ）。
- **Flash-Next の decode で、途中の非同期 eval を 6 層ごとから 2 層ごとにしました**（`_DECODE_MIDLOOP_DEFAULT_LAYERS`）。1 round が 1〜1.6% 短くなります。

## v2.12.3-m1.15 での変更（2026-11-14）

Qwen3.6-35B-A3B 系の prefill を、短い prompt とエージェントの追加ターンで速くしました。decode と、2.9 万トークン以上の cold な prefill は変わりません。ネイティブ拡張は m1.12 から変わっていないので、作り直す必要はありません。

- **prompt の末尾の復元点を、最後の forward の中で記録するようにしました**（`mtplx/qwen35_inforward_boundary.py`、`MTPLX_QWEN35_INFORWARD_BOUNDARY`）。cold な prompt は、末尾に復元点（GDN の境界）を何本か記録するため、最後の chunk をその位置で切って forward していました。2,093 トークンの prompt は 1,024 + 1,024 + 45 行になります。A3B は幅の狭い forward が遅く（MoE の時間は 1 回の forward につき約 217 ms ＋ 1 行あたり 0.345 ms）、2,016 トークンが 2.14 秒なのに 2,094 トークンは 3.0 秒かかっていました。GDN の再帰計算は token の順に進むので、[0, p) と [p, S) に分けて計算しても、p で切った forward と同じ状態になります。この性質を使って、1 回の広い forward の中で境界の状態を記録します（qwen4_exp が使っていた方法を、mlx-lm の `qwen3_5.GatedDeltaNet` と Neural Engine パイプラインの 2 つの半分に広げました）。MoE のモデルだけに入ります。`MTPLX_QWEN35_INFORWARD_BOUNDARY=0` で、以前の切り方に戻ります。

### 不具合の修正

- **34K 前後の cold の prompt で、logits がすべて NaN になる（HTTP 500）**：A3B で、Neural Engine で attention の q/k/v の射影を計算する部分が原因でした。`mtplx/server/openai.py` の先頭 13 万文字（34,179 トークン）の prefill は、m1.5 では毎回失敗しました。射影の出力ごとに有限かどうかを確かめる（そのたびに同期する）と失敗が消えるので、Neural Engine の出力の buffer の順序の問題とみています。この部分を既定で止めました（`MTPLX_ANE_PREFILL_MOE_ATTN=1` で戻ります）。GDN の射影は今までどおり Neural Engine で計算します。31K の prefill は約 3% 遅くなります（30.5 → 31.4 秒）。
- **長い生成が 300 秒で打ち切られる**：GPU の上の round と context-copy の round が、stream の監視（`MTPLX_STREAM_STALL_DEADLINE_S`）の heartbeat を進めていなかったため、ツールの呼び出しの中に長いファイルを書く 2 万トークンの応答（69 tok/s）が途中で止められていました。
- **短い 2 文のメッセージが前半だけになる**：取り消された再送の重複を探す処理で、どちらの半分も短すぎて比較できないとき、一致とみなしていました（`Fix it.   Thanks!` が `Fix it.` になります）。
- **omp のツールの往復で、直前の応答を毎回読み直す**：Qwen3.6 の template は、終わったターンの `<think>` を落とします。同じターンのツールの往復の履歴を保存するとき、いま生成した think まで落としていたため、保存が拒否されていました。

### エージェントでの待ち時間（どのモデルにも効く）

- **1 リクエストごとのサーバーの前処理**：取り消された再送の重複を探す処理が、ユーザーのメッセージのすべての区切りで両方の半分を正規化し直していました（O(n²)）。omp では毎回 80〜100 ms かかっていたのが 2.3 ms になりました。重複になりえない文章は、区切りを調べずに飛ばします（20 万個のランダムな文字列で、今までと同じ結果を返すことを確かめました）。
- **履歴が変わったときの再開位置**：候補の保存点から、一致したトークン数が最も長いものではなく、実際に再開できる位置が最も深いものを選ぶようにしました。omp の会話が 21.9 万トークンまで伸びたあと、その保存点の間隔は 6.4 万トークンまで粗くなっていて、6.2 万トークンで分かれた prompt を 1.9 万トークンから読み直していました（70,078 トークン、308 秒）。1 つ前のターンの保存点からなら 6.2 万トークンから再開できました。
- **最後のユーザーのメッセージの位置の保存点**：Qwen3.6 の template は、次のユーザーのメッセージが来ると、終わったターンの `<think>` を落とします。そのため、次のターンはこの位置の直後から分かれます。ここの保存点を、ターンのツールの往復の間も残すようにしました（`MTPLX_QUERY_EDGE_ANCHOR=0` で止まります）。omp の会話を再生すると、4 ターン目の最初のリクエストの読み直しが 28,906 → 25,750 トークン（50.3 → 35.5 秒）になりました。

### A3B のエージェント向けの既定

- **context-copy**：ファイルを書き直す応答は、多くの行がプロンプトにすでにあります。GPU の上の round（m1.5）の横で、プロンプトと 6 トークン以上そのまま一致したところだけ、続きをコピーの block として検証するようにしました。RAMP のあいまいな一致（3 トークンの手がかりで似た箇所を探す）は使いません（`MTPLX_RAMP_FUZZY=0`）。使うと、言い回しを変えて答える普通の会話で外れが増え、decode が約 7% 遅くなりました。block は 16 トークンから始め、すべて受理されるたびに倍にし（最大 96）、外れたら受理された長さまで縮めます。96 トークンの block は compile した verify の bank で検証します。thinking ありの sampling（温度 0.6）で、ファイルの書き直しが 111.0 → 219.2 tok/s、新しい文章は 104.9 → 110.7 tok/s です（同じセッションで copy なしと比較）。
- **17〜80 行の verify の attention**：16 行を超える verify は、8bit の KV を全部 fp16 に戻してから計算していました。80 行までは split-K の MMA の kernel（4 行ずつ）で計算します。85K の履歴で、17 行が 240 → 127 ms、33 行が 295 → 232 ms です。
- **短いツールの結果の prefill**：深い履歴の後ろに足す 96 トークン以下の prefill を、split-K の MMA の kernel で 8bit のページから直接読むようにしました。160K の履歴に 42 トークンを足すと 0.75 → 0.42 秒、85 トークンで 0.94 → 0.77 秒です。

### decode: GPU の上で round を続けて回す（A3B）

MTP の depth 1 の 1 round（draft → verify → 受理の判定 → cache の確定）を、host が結果を読む前に次の round まで GPU に積むようにしました（`mtplx/resident_decode.py`）。今までは、verify が終わるたびに host が結果を読み、確定と draft を組み立ててから次の verify を出していたので、2K では 1 round（約 19 ms）のうち約 3.7 ms、GPU が止まっていました。

- 受理の判定、次のトークン、GDN の state の選択（capture した行）、attention と MTP の KV の offset の更新を、すべて GPU の上の配列のまま行います。
- host は 1 round 遅れで結果を読み、トークンを出します。停止トークン、max_tokens、中断などで抜けるときは、読み終えていない round の頭まで cache を巻き戻します。そこから今までの loop が、続きをそのまま処理します。
- 積んだ verify の KV の書き込みは、前の round が buffer を持っていても全体をコピーしないよう、その場に書き込みます。入るときに buffer を自分専用にし（session bank と共有していればコピー）、compile の program もほかと分けています。
- **greedy**: 出力は今までの loop と bit 単位で一致します（2K〜30K、停止、複数ターン、session の復元、max_tokens で確認）。
- **sampling**: 1 round で使う 3 つの乱数（draft、受理の判定、bonus または残差）を先に引き、GPU が float32 で判定を予測します。host が 1 round 遅れで、今までと同じ float64 の計算で確かめます。食い違えば、cache と乱数の状態をその round の頭まで巻き戻し、今までの loop がその round を処理します。出力の分布は厳密に正しく、同じ seed なら 2K で 10/10、今までと同じ文章になりました。20K を超える長い履歴では、compile した draft の最下位の bit の違いで、同じ seed でも別の文章になることがあります。

### prefill: Neural Engine を GPU と並行して使う（A3B）

- prefill の chunk を 2 つに分けます。各 GDN 層では、片方の半分の入力の射影（qkv と z）を Neural Engine で計算し、その間に GPU がもう片方の半分の前の層（MoE）を計算します。attention の層の q/k/v も同じように Neural Engine で計算します（attention の本体は今までどおり GPU です）。
- routed expert はトークンごとに変わるので、Neural Engine では計算しません。GPU に残る MoE と並行に動かすことで、時間を稼ぎます。
- Neural Engine の program は層の種類ごとに 1 つで、全層の重みを層ごとの slot に置いたままにします（`native_extensions/ane_ffn` の AneLinear に、重みの slot、入力だけの staging、2048 の入力の幅を足しました。27B の 5120 の幅は今までどおりです）。
- `MTPLX_ANE_PREFILL_MOE=0` で止まります。native 拡張を作り直していない場合は、自動で GPU だけの prefill に戻ります。

### 変更点

**A3B だけに入るもの**（kernel が A3B の形に合わせて書かれているもの）

- **上流の A3B 向けの高速な kernel（row-owned router、combine、gate/up の packing、whole-MoE）を fp16 に移植しました**（`mtplx/kernels/moe_scalar.py`）。上流の kernel は BF16 の checkpoint 専用でした。M1 で使う FP16 版のモデルに合わせて、`bfloat` を `half` にして生成します。
- **whole-MoE を capture_commit・8bit のページ・会話の保存（session bank）の上で使うようにしました**（`MTPLX_M1_WHOLE_MOE_ANY_ROUTE`）。上流では、厳密な比較のための条件（target_prefix、連続したキャッシュ、会話の保存なし）がそろわないと動きません。kernel は MoE ブロックだけを置き換え、キャッシュには触れません。
- **whole-MoE の競合のバグを直しました。** stage 1（routing）の softmax が、行の最大値と合計を `simd_values[0]` に書いて配っていましたが、他の simdgroup がまだ読んでいる間に上書きすることがありました。GPU が混んでいると、同じ入力で選ばれる expert が変わることがありました（40 層を 8 回試して 7 回）。各 simdgroup が自分で部分和を集める形に直しました。上流の BF16 版にも同じコードがあります。
- A3B の verify は、M1 では既定で capture_commit です（v2.12.2-m1.3 から）。

**どの MoE にも入るもの**（config.json の expert の数で MoE と判断します）

- **draft の同期の後回し**（`MTPLX_M1_MOE_DEFERRED_DRAFT`）: depth 1 の greedy の draft を GPU に渡したまま、トークンを verify の入力に使います。値はあとで読みます。
- **bonus と訂正のトークンをまとめて計算**（`MTPLX_M1_MOE_BATCHED_BONUS`）: 全部受理したときの bonus の行も、却下したときの訂正のトークンも、accept の argmax と 1 回の読み出しで済ませます。
- **greedy の chain の 12K の上限を外しました**（dense で決めた値でした）。
- **サンプリングのときの early verify**（`MTPLX_CHAIN_EARLY_VERIFY`）: temperature 1.0 で 2K は 75.8 → 82.2 tok/s、30K は 65.8 → 72.3 tok/s。同じ seed なら出力は一致します。
- **MoE の prefill の gather を expert ごとに区切りました**（`mtplx/kernels/moe_seg_gather_m1.py`、`MTPLX_M1_MOE_SEG_GATHER`）。MLX 0.32.2 の gather_qmm は、tile が expert の境目をまたぐと行列積をやり直します。expert ごとに tile を切り、MLX 自身の `qmm_t_impl` で計算します。結果はビット単位で一致し、最初の呼び出しで形ごとに照合して、合わなければ元の処理に戻します。MoE ブロックは 25.3 → 21.3 ms（2048 トークン）になりました。
- **prefill の chunk を 4,096 トークンに**しました。8K の cold prefill は +6%、30K は +4.5% です。メモリが足りないときは、メモリガードが今までどおり chunk を狭めます。
- **qwen3_next の GDN を持つ MoE だけ**: blocked の GDN prefill、GDN の射影と出力の融合（`MTPLX_GDN_BLOCKED_PREFILL`、`MTPLX_FUSE_GDN_PROJECTIONS`、`MTPLX_FUSED_GDN_OUT`）
- A3B 以外の MoE では計測していません。どれも出力が一致する（または一致を確かめてから使う）変更ですが、速くなるかは確かめていません。

**切り替え**

- `MTPLX_M1_MOE_LANE=0` で、上の起動時の設定をすべて止められます。個々の環境変数を自分で設定すれば、その値が優先されます。

- greedy の要約（3 本）は、両方の版で書き出しが同じでした。
- decode の 1 ラウンドは、2K で 97.5 → 88.3 ms、32K で 105 → 97 ms です（draft と verify の合計）。tok/s には、draft の 8bit 化による受理率の違い（±3%）も入っています。
- 以前の別の計測（huihui 4bit、128K の会話）では、cold prefill が 1,350 → 927 秒でした。

### prefill

- **Neural Engine（ANE）との分担：** 各層の MLP の中間チャンネルの一部（10,240 チャンネル）を ANE で同時に計算します。ANE 側は int8 の活性値（512 ブロックの Hadamard 回転つき）× fp16 の重みです。Splash（Apache-2.0）の ANE の呼び出し方を MLX の上に作り直しました（`native_extensions/ane_ffn/`、`NOTICE`）。
  - prefill の塊を半分に分け、GPU と ANE が交互に休まず動くように重ねます。文脈が 32K までのときだけです。それより長いと GPU の見張り（watchdog）のエラーが出たので、半分ずつ順番に計算します。
  - 非公開の `AppleNeuralEngine.framework` を使います。macOS の更新で使えなくなったときや、ANE の呼び出しが失敗したときは、自動で GPU だけの計算に戻ります。止めるときは `MTPLX_ANE_PREFILL=0`。
  - 品質：greedy で 18 問中 11 問が完全一致でした。KV を q8 と fp16 で切り替えたときの変化と同じくらいです。70 分の連続運転でエラーは出ませんでした。
- **過去の KV に対する attention を metal-flash-attention で：** native 拡張にしました（`native_extensions/mfa_attn/`）。1 層あたり 1.38〜1.51 倍で、新しいトークンが 256 以上のときだけ使います。止めるときは `MTPLX_MFA_PREFILL=0`。
- **q8 の KV を層ごとに 1 回 fp16 に戻してから attention**（`MTPLX_KV_QUANT_PREFILL_DEQUANT=0` で止まる）と、**prefill の線形層を fp16 GEMM で**（ビット単位で同じ結果、`MTPLX_PREFILL_DEQUANT_GEMM=0`）。
- ANE を使うときは、prefill の塊の大きさを 4096 にします（自動のとき）。

### decode

- **verify の attention を 8 simdgroup で**（16K 以上、`MTPLX_GQA_MMA_NSG=4` で元に戻る）と、**MTP の層（fp16）を読み込み時に 8bit に**（`MTPLX_MTP_QUANT_BITS=0` で fp16 のまま）。
- **decode の間だけ、MLX のコマンドバッファの上限を 150 ops / 1,000 MB に**（prefill は MLX の既定のまま。`MTPLX_DECODE_CB_LIMITS=0`）。
- **ホストと GPU の往復を減らしました。** どれも出力は変わりません（同じ seed でビット単位で同じ）。
  - 受理の判定に使う確率を、1 位置ずつではなくまとめて 1 回で読みます（`MTPLX_M1_BATCH_TARGET_DEFAULT=0` で元に戻る）。
  - 12K を超える文脈で、16 層の KV の位置を 1 層ずつ読んでいたのを 1 回にまとめました（`MTPLX_PAGED_OFFSETS_MAX_CONTEXT`）。
  - **draft を GPU 上で 3 段続けて作る chain を既定にしました**（`MTPLX_QWEN4_SAMPLED_DRAFT_CHAIN=0` で 1 段ずつ）。以前は長い文脈で遅くなっていました（段ごとに MTP の KV を丸ごとコピーしていたため）。KV をその場で書き込む命令を native 拡張に追加して直しました（`MTPLX_MTP_INPLACE_KV=0`）。32K で 1 ラウンド −2.3%、110K で −1.7%。
- 3 つを合わせて、32K で 1 ラウンドが約 100 → 95 ms です。
- verify を draft の直後に積む切り替え（`MTPLX_CHAIN_EARLY_VERIFY=1`）も入れましたが、速くならなかったので既定は off です。

### その他

- dense の 4bit・8bit のモデル（Qwen3.8-27B など）は、M1 では turbo の profile を既定にしました（`MTPLX_M1_TURBO_DEFAULT=0` で元に戻る）。MoE はこれまでどおり sustained です。
- ネイティブ拡張は、利用者の環境でビルドが必要です（`scripts/build-m1-native-extensions.sh`、1 分ほど）。ビルドしなくても動きますが、ANE、metal-flash-attention、draft の chain は使われません。手順は USAGE を見てください。
- テスト：本家との差分によるテストの失敗のほか、M1 の既定値を前提にしていないテストがいくつか落ちます（`MTPLX_M1_LONG_CONTEXT=0` で通るものがほとんど）。

## v2.12.2-m1 での変更（2026-10-04）

### 本家 2.12.2 への追従

本家の v2.12.1 と v2.12.2 を取り込みました。
主な中身は、メモリガード（すべての要求の必要メモリを見積もり、足りなければスワップに入る前に 507 で断る）、SSD キャッシュとセッションバンクの改良、ツール呼び出しやストリームの修正などです（本家の CHANGELOG）。
m1.3 で直した「長い生成が約 1.65 万トークンで止まる不具合」は、本家も #526 として別の方法で直しました。
本家の方法（書き込む前に KV を広げ、メモリが足りなければ断る）に置き換え、M1 で使う q8 の「pages」形式の KV でも正しく広がるようにしました。

- 本家 2.12.2 との差は、この版の M1 向けのコードと、下の修正です。
- m1.3 との比較（M1 Max 64GB、Qwen3.8-27B、q8 の KV、greedy、3 ターンの会話）：生成文は 2K / 32K / 128K の 9 ターンすべてで同一でした。最初のプリフィルは 2〜3% 速く（128K で 1492 秒 → 1450 秒）、2 ターン目以降の応答開始は 0.1〜0.15 秒速く、decode は ±1% 以内でした。

### M1 の処理に合わせたメモリの見積もり

本家のメモリガードの見積もりは、本家の処理での実測にもとづいています。
M1 のこの版は処理が違うので、実測に合わせて直しました。

- **プリフィルの作業領域：** この版は M1 でプリフィルを MMA カーネルで行い、スコアの行列を作りません。2,048 行のチャンクで、見積もり 3.15 GB に対し実測は約 2.05 GB でした。M1 では本家の見積もりの 70% にしました（`MTPLX_M1_MMA_PREFILL_SCRATCH_FRACTION`、1 で本家と同じ）。
- **q8 の保存状態からの復元：** この版は q8 の保存状態を、fp16 に戻さずに q8 のページへ直接戻します。本家の見積もりは fp16 に戻してから詰め替える処理として数えていて、11.2 万トークンの会話に 19 トークンを足すだけの要求を 12.99 GB と見積もって断っていました。直した見積もりは 8.84 GB で、実測（11 万トークンの会話に 20 トークンの続き）は 7.38 GB でした。

### エージェントでの長い会話の修正（本家にもある不具合）

omp で思考オン（xhigh）の作業を続けたときに見つかった不具合です。
どれも M1 に限りません。

- **長い思考のあとで会話のキャッシュが外れる：** サーバーは、プロンプトの 25% 以上が前の会話と一致するときに同じ会話とみなします。思考が長いと（7 万トークン以上）、思考の序盤にあるトークンの区切りの違い（同じ文字列で、区切りだけが違う）が 25% を割り、別の会話と判定されて、思考の全体（約 7.8 万トークン）を読み直していました。分かれ目が前のターンで生成した部分の中にあり、同じ文字列に戻るときは、同じ会話とみなすようにしました。
- **ツール呼び出しの引数の空白：** サーバーが引数の値の前後の空白をすべて削っていました。書き込むファイルの末尾の改行や 1 行目の字下げが消え、さらにクライアントが送り返した履歴が生成と 1 文字違うため、会話の保存が見送られて、次の呼び出しで直前の思考（7.4 万トークン）を読み直していました。Qwen の書式で枠になる改行 1 つずつだけを除くようにしました（複数行の値はそのまま、1 行の値は従来どおり前後を削る）。
- **生成の途中で KV を広げられないとき：** 27B の KV はデコード中に広げますが、メモリが足りずに断られると、要求全体が 507 になり、それまでに書いた回答も失われていました。各ラウンドの手前で次のラウンドの分を確保し、断られたらその時点で止めて回答を残すようにしました（`finish_reason: length` と `memory_stop`）。
- **大きなキャッシュ外れの記録：** 1.6 万トークン以上のプロンプトで半分以上を読み直したとき、その理由（会話の判定、保存状態の一覧、直近の削除）をサーバーのログに 1 行で出します。

これらを入れた版で、omp の京都庭園の課題（思考 7.4 万トークン、12 回の呼び出し）が最後まで動きました。

## m1.3 での変更（2026-10-01）

- **長い生成が約 1.65 万トークンで止まる不具合を修正しました。** 本家にも同じ不具合があり、M1 に限らない修正です。
  - サーバーは生成用の KV キャッシュを最初に最大 16,384 トークン分だけ確保し、足りなくなったら増やす設計です。ところが compiled verify が使う形の KV キャッシュには容量を増やす処理がなく、確保した分を使い切ると容量の外に書き込んで値が壊れ、出力が NaN になってエラーで止まっていました。
  - thinking オンで長く考えさせると必ず起きていました（Qwen3.8-27B、xhigh で約 16,530 トークン目）。compiled verify の文脈の上限を下げても直らず、最初から全量を確保する設定（`MTPLX_DYNAMIC_PAGED_KV_MAX_INITIAL_NEW_TOKENS=unlimited`）では起きないことで原因を確定しました。
  - 修正：compiled verify の KV キャッシュにも容量を増やす処理を足し、足りなくなる前に増やすようにしました（1.5 倍か必要量の大きいほう）。17,500 トークンの再現手順と、thinking オンで最大 5.7 万トークンを生成する課題がすべて最後まで動き、速度は変わりませんでした。
  - 修正前の版での回避策は `MTPLX_DYNAMIC_PAGED_KV_MAX_INITIAL_NEW_TOKENS=unlimited` です（要求された生成量の KV を最初に確保するので、メモリを少し多く使います）。

## m1.2 での変更（2026-09-30）

- **SSD キャッシュ（`--ssd-session-cache on`）から再開するときの不具合を修正しました。** 本家にも同じ不具合があり、M1 に限らない修正です。
  - サーバーを再起動したあと、別の会話と共通する先頭部分（エージェントのシステムプロンプトなど）を SSD から再開するとき、一致した長さを 256 トークン単位に切り下げた位置を再開位置として使っていました。GatedDeltaNet を含むモデル（Qwen3.5 / 3.6 / 3.8、Flash-Next）では、その手前の保存位置まで戻って読み直していました。
  - omp（システムプロンプト約 1.9 万トークン）では、保存位置 19,337 に対して 18,432 から再開し、約 1,000 トークンを読み直していました。1 ターン目の TTFT は 10.7 秒 → 3.4 秒になりました。
  - サーバーが動いている間のメモリ上のキャッシュは別の処理なので、影響はありません。公開ベンチ（SSD キャッシュ off）の数値も変わりません。

## m1.1 での変更（2026-09-29）

- **#9 の Metal コマンドバッファの拡大を既定で無効にしました。** decode は速くなりますが（+6〜7%）、MLX のコマンドバッファのメモリ上限を上げると prefill が遅くなります。

- その他：Flash-Next など QSA attention のモデルで、#1 の draft 用の差し替えが本体の全層に及んでいた不具合を修正（27B は変化なし）。

## 総合ベンチマーク結果

- **測定環境：** M1 Max 64GB、Qwen3.8-27B、8-bit KV、greedy デコード、3 ターン会話、各ターン最大 256 トークン（[apple-silicon-llm-bench](https://github.com/shunya1810/apple-silicon-llm-bench)）
- **比較対象：** 本家コミット `1de2b1c`（v2.12.0 ＋ README 更新 1 コミット）。起動オプションは両者で同一で、違いは読み込むコード（`PYTHONPATH`）だけです。「本家 + env」は、同じ本家のコードに上表の「できる」の環境変数をすべて与えたものです。
- **計測日：** 本家と本家 + env は 2026-09-29 に同じセッションで交互に計測しました。本ビルド（タグ `v2.12.0-m1.2`）は 2026-09-30 に同じ計画で単独で計測しました（事前に 2K の確認でマシンの状態が同じことを確かめています）。
- decode は 3 ターンの平均（各ターンは 2 ラウンドの中央値。128K は 1 回）です。

| コンテキスト長 | 本家 decode | 本家 + env decode | 本ビルド decode | 本家 3 ターン総所要時間 | 本ビルド 3 ターン総所要時間 |
|---|---|---|---|---|---|
| **2K** | 23.6 tok/s | 27.2 tok/s | **29.3 tok/s** | 41.8 秒 | **36.0 秒** |
| **32K** | 14.0 tok/s | 15.3 tok/s | **25.5 tok/s** | 5.0 分 | **4.6 分** |
| **64K** | 8.7 tok/s | 7.8 tok/s | **23.4 tok/s** | 11.3 分 | **10.1 分** |
| **128K** | 5.0 tok/s | 4.6 tok/s | **19.0 tok/s** | 30.6 分 | **24.9 分** |

- `v2.12.0-m1`（2026-09-29 に本家と同じセッションで計測）は、decode が 31.8 / 27.0 / 24.3 / 19.6 tok/s、3 ターン総所要時間が 35.2 秒 / 4.7 分 / 10.9 分 / 25.3 分でした。m1.2 は decode が 3〜9% 低い代わりに、prompt の読み込みが速くなっています（「m1.1 での変更」）。
- サンプリング（temperature 1.0、top-p 0.95、top-k 20、最大 512 トークン）では、本ビルドが 2K / 32K / 64K で 27.5 / 25.2 / 23.8 tok/s、本家が 23.2 / 14.2 / 8.9 tok/s、本家 + env が 26.4 / 14.2 / 8.2 tok/s、Splash 1.1.0-m1 が 32.7 / 25.8 / 22.0 tok/s でした。
- Splash 1.1.0-m1 との比較：decode は 64K まで Splash が速い（2K〜8K で 13%、32K〜64K で 3〜6%。128K は本ビルドが 2% 速い）一方、3 ターン総所要時間は本ビルドが 2K〜128K で 5〜15% 短いです。短いプロンプト・推論ありの条件では、Splash の decode が 29% 速く、1 トークンあたりのエネルギーも約 3 分の 2 です。

> **読み方の注意：**
> - 総所要時間の差が decode ほど大きくないのは、1 ターン目のコールド prefill（64K で約 10 分）が時間の大半を占めるためです。本ビルドの prefill は 2K〜8K で本家と同じ、32K で 2.5% 遅く、64K で 4%、128K で 14% 速いです。
> - 各ターンの生成が 256 トークンと短い条件です。生成が長い使い方では decode の差が大きく効きます。
> - ピークメモリは本ビルドの方が少ないですが（128K で 43.5 GB 対 52.4 GB）、Splash（22〜26 GB）よりはかなり多いです。
