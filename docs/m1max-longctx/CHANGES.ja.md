## v2.12.2-m1.12 での変更（2026-10-31）

Qwen4 の公開に向けた下準備と、scale が bf16 のパックの prefill の修正です。README の表のモデル（どれも scale は fp16）の速さは m1.11 と同じです。ネイティブ拡張では `qsa_kernels` がビルドの対象に加わりました。使うのは Qwen4 系の経路だけなので、m1.11 から更新するときは、その経路を使う場合だけ `scripts/build-m1-native-extensions.sh` を実行してください。`mfa_attn` と `ane_ffn` は m1.11 から変わっていません。

- **scale が bf16 の dense のパックで、512 トークン以上のプロンプトが NaN で止まる問題を直しました。** v2.12.2-m1.1 からありました。M1 では、512 行以上の prefill で計算の一部を Neural Engine に任せます。そのための重みを用意する kernel が、量子化の scale と bias を fp16 として読んでいました。bf16 のパックでは bf16 のビット列を fp16 と解釈するので値がまったく別のものになり、logits がすべて NaN になっていました。mlx-community の Qwen3.8-27B-4bit（scale が bf16）では、1,536 トークンの prefill で logits がすべて NaN になり（`MTPLX_ANE_PREFILL=0` なら有限）、サーバーでは 2,400 トークンのプロンプトが HTTP 500（non_finite_logits）で止まりました。Neural Engine に渡す scale と bias を呼び出しごとに fp16 に変換するようにして、同じプロンプトに正しく答えるようになりました。
  - README の表のモデル（Youssofal の FP16 パックと、MTPLX forge で変換した 3 つ）は scale が fp16 なので、影響はありませんでした。変換も何もしません。
  - mlx-community の 4bit 変換には MTP のヘッドが入っていないので、MTPLX は speculative decoding なしで動かします（本家も同じです）。
- **Qwen4 の公開に向けた下準備をしました（実際の Qwen4 のモデルでは確かめていません）。** 本家 MTPLX の `qwen4_exp` の経路は、Qwen3.8-Flash-Next の形（hidden 2560、MoE、query 24 / KV 2 ヘッド）を前提に書かれています。Qwen4 のモデルが同じアーキテクチャを別の大きさで使った場合に備えて、この経路がほかの形も扱えるようにし、M1 での速さを調整しました。確かめたのは、ランダムな重みで Qwen3.8-27B と同じ幅にした合成モデル（hidden 5120、64 層、query 24 / KV 4 ヘッド、dense の MLP、fp16 と bf16）です。
  - dense の MLP の層を扱えるようにしました。読み込み時に射影をまとめる処理が幅 2560 を前提にしていて、幅 5120 のパックは読み込めなかったので、モデルの幅を読むようにしました。
  - 疎な attention（QSA）の prefill の kernel が query 24 / KV 2 ヘッドにしか対応しておらず、ほかのヘッド構成では 3.2 万トークンを超えると、すべての attention の層が密な計算に戻っていました。kernel をほかのヘッド構成（GQA 1〜16）でも使えるようにし、M1 で疎な計算に切り替える長さを 1.6 万トークンにしました。3.6 万トークンの位置の 2,048 行のチャンクで、attention は 1 層あたり 403 → 245 ms、チャンク全体は 15.9 → 14.3 秒になりました。
  - M1 向けの verify の量子化行列積の kernel を、この経路でも使うようにしました。depth 3、2K の verify 1 回が 196 → 135 ms です。さらに hyper-connection の読み出しを 1〜4 行用の kernel にして、135 → 126 ms になりました。
  - M1 の GPU には bf16 の演算がないので、この系統の bf16 のパックは既定で fp16 に変換して動かします。合成モデルでは、8K の prefill が約 1.4 倍（169 tok/s）になり、verify は約 10% 短くなりました。`MTPLX_M1_FP16_CAST=0` で切れます。ほかの系統では `MTPLX_M1_FP16_CAST=1` で使えます（fp16 のパックでは何もしません）。
  - Flash-Next 専用の融合 kernel（幅 2560 専用で、環境変数でオンにするもの）が、ほかの幅のモデルで使われないようにしました。
  - 合成モデル（fp16）をサーバーで動かすと、prefill は 1.6K で 160 tok/s、7.7 万トークンで 133 tok/s、verify 1 回は 120 ms（1.6K）でした。重みがランダムなので draft は当たらず、decode の速さはまだ測れていません。
- **README の表のモデルの速さは変わりません。** m1.11 と同じプロンプトで、サーバーを交互に 2 回ずつ起動して比べました（SSD のセッションキャッシュはオフ。1.6K は 6 回、ほかは 2 回の平均。25K は各 1 回）。Qwen3.8-27B は prefill が 1.6K で 183 → 185 tok/s、25K で 192 → 192 tok/s、verify 1 回が 88.5 → 87.1 ms です。Qwen3.6-35B-A3B は prefill が 1.6K で 1,018 → 1,020 tok/s、6.3K で 1,097 → 1,103 tok/s、verify 1 回が 12.0 → 11.9 ms です。decode の tok/s は draft の当たり方で ±5% ほど揺れるので、verify 1 回の時間で比べています。

## v2.12.2-m1.11 での変更（2026-10-25）

長いプロンプトの prefill の attention と、thinking を切り替えたときのキャッシュを直しました。ネイティブ拡張（`mfa_attn`）が変わったので、`scripts/build-m1-native-extensions.sh` で作り直してください。

- **長いプロンプトの prefill で、attention の途中の和が fp16 の上限を超えて NaN になる問題を直しました。** M1 では、キャッシュした履歴（8K トークン以上）への attention を、metal-flash-attention にならった kernel（head_dim 256）で計算しています。この kernel は、128 個のキーごとに、正規化する前の出力の和（最大で 確率の和 × |v|）を出力バッファに書き出し、次のブロックで読み戻します。このバッファが fp16 だったので、長いプロンプトでは和が 65,504 を超えて inf になり、causal な末尾との合成で NaN になっていました。[apple-silicon-llm-bench](https://github.com/shunya1810/apple-silicon-llm-bench) の bench 3 では、Qwen3.8-27B で 19.2 万〜25.6 万トークンの cold のプロンプト 9 件のうち 8 件が、logits がすべて NaN になって止まりました（245K の文脈で、入力がすべて有限のまま 1 行が inf になっていました）。NaN にならなかった行も精度が落ちていて、失敗した呼び出しを再生すると、fp32 で計算した基準との差の最大は 2.6 でした。出力を kernel の中でも拡張の出力でも fp32 で持つようにして、差は 0.037（フォーク自身の kernel と同じ程度）になりました。kernel の時間は 1% 以内で変わりません（M1 Max、履歴 32K〜245K、512 行と 2,048 行のチャンク）。
  - 修正後、27B の 19.2 万〜25.6 万トークンの 6 つのセル（agent、英語、日本語、code）はすべて通りました。
  - 修正前も NaN にならずに通っていた 27B の 224K では、decode が thinking あり 10.9 → 20.6 tok/s、なしで 9.0 → 18.0 tok/s になりました。精度が落ちた行が KV と MTP の履歴に残り、出力と draft の当たり方が変わっていたと考えています（MTP の受理率はログに残っておらず、確かめていません）。
  - 3.2 万トークン以上では、27B でも A3B でも出力が修正前と変わります。8K では同じでした。decode の速さの差は、3.2 万〜12.8 万トークンでは数 % です。
- **同じプロンプトで thinking の有無を切り替えると、プロンプトをすべて読み直していた問題を直しました。** 会話の保存を探すときの識別に thinking の有無が入っていたので、thinking ありの会話と同じプロンプトに thinking なしで質問すると、使える保存が見つかりませんでした（本家 v2.12.2 も同じ）。保存はトークン列で完全一致を確かめていて、thinking の違いがプロンプトに現れる場合はトークンの違いとして検出されるので、識別から外しました。thinking なしに切り替えた直後の応答までの時間は、27B の 128K で 996 秒 → 1.8 秒、A3B の 256K で 1,036 秒 → 7.1 秒です。更新前に保存した会話は、更新後の最初の 1 回だけ読み直します。

## v2.12.2-m1.10 での変更（2026-10-20）

長いプロンプトの prefill と、会話の続きの扱いを直しました。A3B（MoE）の速さとメモリは m1.9 と同じです。

- **27B などの dense のモデルで、3.2 万トークンを超えるプロンプトの prefill の一部の行が誤って計算される問題を直しました（v2.12.2-m1.1 から）。** M1 では、prefill の FFN の一部を Neural Engine で計算しています。文脈が 3.2 万トークンを超えると、GPU と Neural Engine で並べて計算する方式から、層ごとに Neural Engine を呼ぶ方式に切り替わります。この方式では、4,096 行のチャンクを 2,048 行ずつ 2 回に分けて Neural Engine に送ります。ところが、1 回目の結果を出力バッファから取り出す前に、2 回目の実行がバッファを上書きしていました。そのため、チャンクの前半 2,048 行は、FFN のうち Neural Engine が受け持つ部分（7,680 チャンネル）を後半の行の値で計算していました。前半の行の hidden から次のトークンを予測させると、当たる割合は 29〜39% でした（Neural Engine を使わない場合は 87〜96%）。誤った値は KV と MTP の履歴に残るので、長いプロンプトへの応答の質に影響していた可能性があります。1 回目の結果を取り出してから 2 回目を実行するように直し、前半の行も Neural Engine を使わない場合と同じ値になりました。MoE のモデル（Qwen3.6-35B-A3B など）は、この経路を使わないので影響はありません。
- **1 つのターンが終わった直後に次のリクエストが来ると、プロンプトを読み直していた問題を直しました。** 27B で思考が途中で打ち切られたターンの直後に次のターンを送ると、32K の会話で 3,062 トークン（応答の開始まで 22 秒）、246K の会話ではプロンプト全体（51 分）を読み直していました。直前のターンの復元に使った位置をチェックポイントとして残し、復元に使った保存を手放したターンでもプロンプトを保存するようにしました。同じ手順で、32K は 83 トークンの読み込みで 1.1 秒、246K は 3.3 秒で応答を始めます。
- **会話の保存が二重に残っていたのを直しました。** prefill の直後の保存と、回答の終わりの保存が 64 トークンしか違わないのに、両方残っていました（64K で各 3.8 GB）。prompt の終わりのチェックポイントは 1 トークン手前に置かれるので、長い保存が短い保存を置き換える条件を満たしていませんでした。1 トークン下のチェックポイントで代わりになるようにして、64K のターンの後の wired が 2.9 GB 減りました（`MTPLX_SESSION_BANK_SUPERSEDE_TAIL_SLACK`）。
- **dense のモデルでは、19.2 万トークンを超えるプロンプトの prefill の間、KV を fp16 で持ち、読み終えてから 8bit に詰め直すようにしました。** 27B の 253K のプロンプトで、8bit のページに直接書き込む方式はメモリのピークが 51.3 GB になり、上の修正を入れた状態ではメモリガードが HTTP 507 で止めていました。fp16 で持つ方式では 43.4 GB で、prefill の速さは同じです（`MTPLX_M1_PAGED_PREFILL_MAX_CONTEXT`）。ただし、3 ターンの会話のベンチ（246K）では、wired のピークが 42.0 → 44.4 GB に増えました。MoE のモデル（Qwen3.6-35B-A3B など）は、メモリに余裕があり、fp16 で持つと prefill が遅くなったので、これまでどおり 8bit のページに直接書き込みます。
- **MTP の深さを上げる実験用の設定を追加しました（既定では無効）。** 8 行の verify の行列積を simdgroup MMA で計算する kernel（`MTPLX_M1_MMA8=1`）、8bit の KV の verify attention で 5〜8 行を 4 行ずつに分ける処理（既定で有効。深さ 4 以上のときだけ効きます）、深さ 6 以上でコンパイル済みの verify の器を深さ + 1 に広げる処理、サーバーの深さの上限を上げる `MTPLX_EXPERIMENT_DEPTH_CEILING` です。M1 Max では、深さ 7 は改良後も深さ 3 より 2K で 5%、32K で 15% 遅く、既定の深さは変えていません。

## v2.12.2-m1.9 での変更（2026-10-18）

- **1 つのサーバーで大きな会話を何回か続けたあと、長いプロンプトの読み込みが HTTP 507 で止まる問題を直しました。** 27B で 8K、32K、64K の会話を続けたあと、新しい 128K のプロンプトを読み込むと、途中で「メモリ不足」として止まっていました。このとき、使っていない会話の状態が RAM に 9〜11 GB 残っていました。メモリガードが会話の状態を手放すのは 1 回の読み込みにつき 1 回だけで、手放す量も、次の 1 チャンクに足りない分だけだったためです。足りなくなるたびに、手放せる分がある限り、同じ確認の中でも次のチャンクでも繰り返し手放すようにしました（1 回の読み込みで最大 8 回）。同じ手順で 128K の読み込みが通りました（2 回で 7.0 GB を手放しました）。

## v2.12.2-m1.8 での変更（2026-10-18）

M1 向けの変更が効くモデルと起動の経路を広げました。どれも、出力の分布は変わりません。

- **Qwen3.5・3.6・3.8 系のモデルを、M1 では既定で `turbo` で起動するようにしました。** これまで `turbo` になるのは、本家が指定した 27B の主力モデルと、一部の dense のモデルだけでした。ほかは `sustained` になり、verify 用の kernel が使われていませんでした。系統は `config.json` の `model_type` で判定するので、派生モデルや自分で forge したモデルも対象です。Qwen3.6-35B-A3B を `bin/mtplx serve` でプロファイルを指定せずに起動したとき、decode が 74.4 → 109.7 tok/s になりました。`MTPLX_M1_TURBO_DEFAULT=0` で本家の既定に戻せます。
- **アプリから起動した Qwen3.6-35B-A3B で、M1 の A3B 用の経路を使うようにしました。** アプリは、このモデルに本家の `--verify-strategy target_prefix` を常に付けて起動します。そのため、`capture_commit` の上で動く resident decode と context-copy が、アプリのチャットでは使われていませんでした（decode 約 60 tok/s）。アプリからの起動（`--app-launch-id`）で、1 件ずつ処理する serial のときは M1 の既定に置き換えます。アプリと同じ引数と環境変数で起動して、108.4 tok/s になりました。CLI で `target_prefix` を指定した場合と、batched の場合は、指定どおりです。
- **Qwen3.6-35B-A3B の派生モデル（Ornith-1.5-35B-A3B など）にも、A3B 用の経路を使うようにしました。** これまではモデル ID で判定していたので、派生モデルは対象外でした。同じ構成（expert 256 個、1 トークンあたり 8 個、隠れ層の幅 2048、40 層、本体が 4bit・64 値ごと）なら対象にします。自分で forge したモデルとの違いは、読み込み時に揃えます。MTP の expert が fp16 なら 4bit・32 値ごとに量子化し（公式の版と同じ形）、GDN の小さなパラメータ（`A_log`、`dt_bias`、`conv1d`）の型は、`config.json` の記載ではなく実際の重みに合わせます。Ornith-1.5-35B-A3B の decode が 83.8 tok/s（それまでの最良、深さ 2）から 111.8 tok/s（深さ 1）になりました。
- **`mtplx tune` と forge の深さの確認を、実際に起動するときの profile で測るようにしました。** これまでは `sustained` で測っていたので、forge が記録する最適な深さが、`turbo` で動かすときの最適な深さと違っていました。Swift-1.5-Qwen3.8-27b（4bit・64 値ごと）では、forge が深さ 2 を記録していましたが、`turbo` では深さ 3（32.9 tok/s。深さ 2 は 23.1 tok/s）が最速です。
- **スクリプトを 2 つ追加しました。** `scripts/m1-depth-sweep.py` は、深さ 1〜3 を `turbo`・256K・8bit の KV で測って、一番速い深さを示します（`--apply-app` でアプリの設定に書き込みます）。`scripts/m1-app-use-checkout.sh` は、アプリがどこから開かれても、この checkout のエンジンを使うように設定します。

## v2.12.2-m1.7 での変更（2026-10-17）

- **OpenCode 2 で応答が途中で切れる問題を直しました。** 最後のストリームのチャンクに付く `mtplx_stats` が 17〜19 KB あり、OpenCode 2 の SSE の上限（16 KB）を超えて `SseEventTooLarge` で止まっていました。最後のチャンクは 12 KB 前後に収まるようにしています（`_cap_stream_stats`）。OpenCode 2.0.31 で実機の確認ずみです。
- **短い suffix の split-K attention を M1 全般の既定にしました（27B も対象）。** 8bit の KV の履歴に短いツール結果を足す prefill が、27B で 32K の履歴の 43 トークンは 0.661→0.610 秒、64K では 0.854→0.728 秒になります。60K の文脈で、有効と無効の greedy 出力は一致しました。`MTPLX_KV_QUANT_SPLITK_MAX_Q=0` で無効にできます。

## v2.12.2-m1.6 での変更（2026-10-17）

thinking ありのエージェント（omp など）で Qwen3.6-35B-A3B を使うときの、待ち時間と失敗を減らしました。普通の会話の decode は、2K では m1.5 と同じで、32K では 3.8% 遅くなります（下の表）。dense のモデル（27B）は、m1.5 と同じ条件で 2 回ずつ交互に計測し、greedy の出力が一致しました（34K のプロンプトを含みます）。

### Qwen3.6-35B-A3B での結果

[apple-silicon-llm-bench](https://github.com/shunya1810/apple-silicon-llm-bench) の 3 ターンの会話（temperature 0）で、m1.5 と m1.6 を 2026-10-17 の朝に交互に 2 回ずつ計測しました。

| | v2.12.2-m1.5 | v2.12.2-m1.6 |
|---|---|---|
| decode、2K（3 ターン × 2 回の平均） | 106.3 tok/s | 105.7 tok/s |
| decode、32K（同上） | 84.1 tok/s | 80.9 tok/s |
| 32K の 1 ターン目の応答開始（2 回目） | 33.0 秒 | 34.0 秒 |
| 会話全体、2K / 32K（2 回目） | 9.9 秒 / 44.1 秒 | 9.8 秒 / 45.0 秒 |

- 32K の decode は 3.8% 遅くなります。深い文脈では、context-copy がプロンプトの定型の書式と完全に一致したところから別の続きを写し、外れることがあるためです。次のバージョンで、copy を始める条件を詰めます。
- 32K の応答開始は、Neural Engine での attention の射影を止めた分（下の「不具合の修正」）だけ長くなります。
- エージェントの使い方で差が出るのは次の 2 つです（下の「A3B のエージェント向けの既定」）。thinking ありのファイルの書き直しは 111.0 → 219.2 tok/s です。深い履歴の後ろに足す短いツールの結果の読み込みは、160K に 42 トークンで 0.75 → 0.42 秒です。

### 不具合の修正

- **34K 前後の cold の prompt で、logits がすべて NaN になる（HTTP 500）**：A3B で、Neural Engine で attention の q/k/v の射影を計算する部分が原因でした。`mtplx/server/openai.py` の先頭 13 万文字（34,179 トークン）の prefill は、m1.5 では毎回失敗しました。射影の出力ごとに有限かどうかを確かめる（そのたびに同期する）と失敗が消えるので、Neural Engine の出力の buffer の順序の問題とみています。この部分を既定で止めました（`MTPLX_ANE_PREFILL_MOE_ATTN=1` で戻ります）。GDN の射影は今までどおり Neural Engine で計算します。31K の prefill は約 3% 遅くなります（30.5 → 31.4 秒）。
- **長い生成が 300 秒で打ち切られる**：GPU の上の round と context-copy の round が、stream の監視（`MTPLX_STREAM_STALL_DEADLINE_S`）の heartbeat を進めていなかったため、ツールの呼び出しの中に長いファイルを書く 2 万トークンの応答（69 tok/s）が途中で止められていました。
- **短い 2 文のメッセージが前半だけになる**：取り消された再送の重複を探す処理で、どちらの半分も短すぎて比較できないとき、一致とみなしていました（`Fix it.   Thanks!` が `Fix it.` になります）。
- **omp のツールの往復で、直前の応答を毎回読み直す**：Qwen3.6 の template は、終わったターンの `<think>` を落とします。同じターンのツールの往復の履歴を保存するとき、いま生成した think まで落としていたため、保存が拒否されていました。
- **macOS が GPU の command を止めたときに、リクエストが失敗する**：画面がついている Mac で長い prefill をすると、macOS が GPU の command を止めることがあります（`kIOGPUCommandBufferCallbackErrorImpactingInteractivity`）。最初のトークンを出す前なら、chunk の幅を半分にして自動でやり直します（`MTPLX_GPU_ABORT_RETRIES`、既定 2 回）。A3B では、Neural Engine の prefill を 32K キーまでにし（それ以上の長さで中断が起きていました）、prefill の 1 chunk の行数 × 文脈の長さに上限を設けました。

### エージェントでの待ち時間（どのモデルにも効く）

- **1 リクエストごとのサーバーの前処理**：取り消された再送の重複を探す処理が、ユーザーのメッセージのすべての区切りで両方の半分を正規化し直していました（O(n²)）。omp では毎回 80〜100 ms かかっていたのが 2.3 ms になりました。重複になりえない文章は、区切りを調べずに飛ばします（20 万個のランダムな文字列で、今までと同じ結果を返すことを確かめました）。
- **履歴が変わったときの再開位置**：候補の保存点から、一致したトークン数が最も長いものではなく、実際に再開できる位置が最も深いものを選ぶようにしました。omp の会話が 21.9 万トークンまで伸びたあと、その保存点の間隔は 6.4 万トークンまで粗くなっていて、6.2 万トークンで分かれた prompt を 1.9 万トークンから読み直していました（70,078 トークン、308 秒）。1 つ前のターンの保存点からなら 6.2 万トークンから再開できました。
- **最後のユーザーのメッセージの位置の保存点**：Qwen3.6 の template は、次のユーザーのメッセージが来ると、終わったターンの `<think>` を落とします。そのため、次のターンはこの位置の直後から分かれます。ここの保存点を、ターンのツールの往復の間も残すようにしました（`MTPLX_QUERY_EDGE_ANCHOR=0` で止まります）。omp の会話を再生すると、4 ターン目の最初のリクエストの読み直しが 28,906 → 25,750 トークン（50.3 → 35.5 秒）になりました。

### A3B のエージェント向けの既定

- **context-copy**：ファイルを書き直す応答は、多くの行がプロンプトにすでにあります。GPU の上の round（m1.5）の横で、プロンプトと 6 トークン以上そのまま一致したところだけ、続きをコピーの block として検証するようにしました。RAMP のあいまいな一致（3 トークンの手がかりで似た箇所を探す）は使いません（`MTPLX_RAMP_FUZZY=0`）。使うと、言い回しを変えて答える普通の会話で外れが増え、decode が約 7% 遅くなりました。block は 16 トークンから始め、すべて受理されるたびに倍にし（最大 96）、外れたら受理された長さまで縮めます。96 トークンの block は compile した verify の bank で検証します。thinking ありの sampling（温度 0.6）で、ファイルの書き直しが 111.0 → 219.2 tok/s、新しい文章は 104.9 → 110.7 tok/s です（同じセッションで copy なしと比較）。
- **17〜80 行の verify の attention**：16 行を超える verify は、8bit の KV を全部 fp16 に戻してから計算していました。80 行までは split-K の MMA の kernel（4 行ずつ）で計算します。85K の履歴で、17 行が 240 → 127 ms、33 行が 295 → 232 ms です。
- **短いツールの結果の prefill**：深い履歴の後ろに足す 96 トークン以下の prefill を、split-K の MMA の kernel で 8bit のページから直接読むようにしました。160K の履歴に 42 トークンを足すと 0.75 → 0.42 秒、85 トークンで 0.94 → 0.77 秒です。

### decode: GPU の上で round を続けて回す（A3B）

MTP の depth 1 の 1 round（draft → verify → 受理の判定 → cache の確定）を、host が結果を読む前に次の round まで GPU に積むようにしました（`mtplx/resident_decode.py`）。今までは、verify が終わるたびに host が結果を読み、確定と draft を組み立ててから次の verify を出していたので、2K では 1 round（約 19 ms）のうち約 3.7 ms、GPU が止まっていました。

- 受理の判定、次のトークン、GDN の state の選択（capture した行）、attention と MTP の KV の offset の更新を、すべて GPU の上の配列のまま行います。
- host は 1 round 遅れで結果を読み、トークンを出します。停止トークン、max_tokens、中断などで抜けるときは、読み終えていない round の頭まで cache を巻き戻します。そこから今までの loop が、続きをそのまま処理します。
- 積んだ verify の KV の書き込みは、前の round が buffer を持っていても全体をコピーしないよう、その場に書き込みます。入るときに buffer を自分専用にし（session bank と共有していればコピー）、compile の program もほかと分けています。
- **greedy**: 出力は今までの loop と bit 単位で一致します（2K〜30K、停止、複数ターン、session の復元、max_tokens で確認）。
- **sampling**: 1 round で使う 3 つの乱数（draft、受理の判定、bonus または残差）を先に引き、GPU が float32 で判定を予測します。host が 1 round 遅れで、今までと同じ float64 の計算で確かめます。食い違えば、cache と乱数の状態をその round の頭まで巻き戻し、今までの loop がその round を処理します。出力の分布は厳密に正しく、同じ seed なら 2K で 10/10、今までと同じ文章になりました。20K を超える長い履歴では、compile した draft の最下位の bit の違いで、同じ seed でも別の文章になることがあります。

|---|---|---|
| 2K | 88.3 tok/s | 102.7 tok/s |
| 30K | 77.6 tok/s | 82.4 tok/s |
| 115K | 58.1 tok/s | 59.7 tok/s |

- `MTPLX_M1_RESIDENT_DECODE=0` で止まります（sampling だけを止めるときは `MTPLX_M1_RESIDENT_SAMPLED=0`、KV の直接の書き込みを止めるときは `MTPLX_M1_RESIDENT_INPLACE_KV=0`）。画像つきのリクエスト、grammar の制約、penalty などは対象外で、今までの loop で動きます。

### prefill: Neural Engine を GPU と並行して使う（A3B）

- prefill の chunk を 2 つに分けます。各 GDN 層では、片方の半分の入力の射影（qkv と z）を Neural Engine で計算し、その間に GPU がもう片方の半分の前の層（MoE）を計算します。attention の層の q/k/v も同じように Neural Engine で計算します（attention の本体は今までどおり GPU です）。
- routed expert はトークンごとに変わるので、Neural Engine では計算しません。GPU に残る MoE と並行に動かすことで、時間を稼ぎます。
- Neural Engine の program は層の種類ごとに 1 つで、全層の重みを層ごとの slot に置いたままにします（`native_extensions/ane_ffn` の AneLinear に、重みの slot、入力だけの staging、2048 の入力の幅を足しました。27B の 5120 の幅は今までどおりです）。
- `MTPLX_ANE_PREFILL_MOE=0` で止まります。native 拡張を作り直していない場合は、自動で GPU だけの prefill に戻ります。

### 変更点

**A3B だけに入るもの**（kernel が A3B の形に合わせて書かれているもの）

- **上流の A3B 向けの高速な kernel（row-owned router、combine、gate/up の packing、whole-MoE）を fp16 に移植しました**（`mtplx/kernels/moe_scalar.py`）。上流の kernel は BF16 の checkpoint 専用でした。M1 で使う FP16 版のモデルに合わせて、`bfloat` を `half` にして生成します。
- **whole-MoE を capture_commit・8bit のページ・会話の保存（session bank）の上で使うようにしました**（`MTPLX_M1_WHOLE_MOE_ANY_ROUTE`）。上流では、厳密な比較のための条件（target_prefix、連続したキャッシュ、会話の保存なし）がそろわないと動きません。kernel は MoE ブロックだけを置き換え、キャッシュには触れません。
- **whole-MoE の競合のバグを直しました。** stage 1（routing）の softmax が、行の最大値と合計を `simd_values[0]` に書いて配っていましたが、他の simdgroup がまだ読んでいる間に上書きすることがありました。GPU が混んでいると、同じ入力で選ばれる expert が変わることがありました（40 層を 8 回試して 7 回）。各 simdgroup が自分で部分和を集める形に直しました。上流の BF16 版にも同じコードがあります。
- A3B の verify は、M1 では既定で capture_commit です（v2.12.2-m1.3 から）。

**どの MoE にも入るもの**（config.json の expert の数で MoE と判断します）

- **draft の同期の後回し**（`MTPLX_M1_MOE_DEFERRED_DRAFT`）: depth 1 の greedy の draft を GPU に渡したまま、トークンを verify の入力に使います。値はあとで読みます。
- **bonus と訂正のトークンをまとめて計算**（`MTPLX_M1_MOE_BATCHED_BONUS`）: 全部受理したときの bonus の行も、却下したときの訂正のトークンも、accept の argmax と 1 回の読み出しで済ませます。
- **greedy の chain の 12K の上限を外しました**（dense で決めた値でした）。
- **サンプリングのときの early verify**（`MTPLX_CHAIN_EARLY_VERIFY`）: temperature 1.0 で 2K は 75.8 → 82.2 tok/s、30K は 65.8 → 72.3 tok/s。同じ seed なら出力は一致します。
- **MoE の prefill の gather を expert ごとに区切りました**（`mtplx/kernels/moe_seg_gather_m1.py`、`MTPLX_M1_MOE_SEG_GATHER`）。MLX 0.32.2 の gather_qmm は、tile が expert の境目をまたぐと行列積をやり直します。expert ごとに tile を切り、MLX 自身の `qmm_t_impl` で計算します。結果はビット単位で一致し、最初の呼び出しで形ごとに照合して、合わなければ元の処理に戻します。MoE ブロックは 25.3 → 21.3 ms（2048 トークン）になりました。
- **prefill の chunk を 4,096 トークンに**しました。8K の cold prefill は +6%、30K は +4.5% です。メモリが足りないときは、メモリガードが今までどおり chunk を狭めます。
- **qwen3_next の GDN を持つ MoE だけ**: blocked の GDN prefill、GDN の射影と出力の融合（`MTPLX_GDN_BLOCKED_PREFILL`、`MTPLX_FUSE_GDN_PROJECTIONS`、`MTPLX_FUSED_GDN_OUT`）
- A3B 以外の MoE では計測していません。どれも出力が一致する（または一致を確かめてから使う）変更ですが、速くなるかは確かめていません。

**切り替え**

- `MTPLX_M1_MOE_LANE=0` で、上の起動時の設定をすべて止められます。個々の環境変数を自分で設定すれば、その値が優先されます。
- 設定はサーバーのプロセス（アプリと `mtplx serve`）にだけ渡し、dense のモデルには渡しません。CLI の `run` / `ask` の 1 回だけの生成には入りません。

## v2.12.2-m1.2 での変更（2026-10-13）

v2.12.2-m1.1 では、256K の会話がメモリガードに断られていました（1 ターン目で「見積もり 54.7 GiB、上限 48 GiB」）。
`--allow-swap` で同じ会話を流すと、スワップを使わずにピーク 53.2 GB で最後まで動きました。つまり見積もりと上限のほうが実際と合っていなかったので、M1 系の Mac に限って直しました。

| 256K の会話（3 ターン、q8 の KV） | m1.1 | m1.2 |
|---|---|---|
| 既定の設定で | 1 ターン目で拒否 | **3 ターンとも完了** |
| 1 ターン目の prefill | 58.9 分（`--allow-swap`） | 58.5 分 |
| decode | 14.4 tok/s | 14.4 tok/s |
| 2 ターン目以降の応答開始 | 3.0 秒 | 2.9 秒 |
| メモリのピーク（Mac 全体の固定分） | 53.2 GB | **50.1 GB** |

- **長いプロンプトは q8 のページに直接 prefill します**（32K トークン以上、`MTPLX_M1_PAGED_PREFILL=0` で元に戻る）。
  - これまでは、全幅の fp16 で KV を書いてから q8 に詰め替えていました。256K では fp16 の KV が約 17 GB、q8 のページが約 10 GB です。
  - prefill の速さは同じでした（26K で 207 tok/s 対 207、50K で 187 対 185）。増えるメモリは小さく（26K で +7.1 GB 対 +8.6、50K で +9.9 対 +11.7）、greedy の答えは 26K と 50K で一致しました。
  - 32K 未満はこれまでどおりです（8K では答えが 73 文字目から分かれ、節約は 1 GB 未満のため）。
- **メモリガードの見積もりを M1 の処理に合わせました。**
  - 512 行の塊（16 万トークン超）で、文脈 1 トークンあたり fp16 の 1 行分を作業領域として足していました。M1 の MMA の prefill では、その分は q8 の KV を戻す分としてすでに数えていたので、二重計上でした（23 万トークンで 15 GiB）。
  - fp16 から q8 への詰め替えを、全層同時の分で見積もっていました。M1 では 1 層ずつ詰め替えて、済んだ層の fp16 を捨てます。
  - q8 のページに直接 prefill するときに、bf16 のミラー（全幅の作業用コピー）の分を見積もっていました。M1 の MMA の prefill はページを直接読むので、ミラーは作りません。
  - 257K のプロンプトで、見積もりの増加は 31.9 → 11.5 GiB です。
- **M1 系（RAM 128 GB 未満）のエンジンの上限を、RAM の 75% から 13/16 に上げました**（64 GB で 48 → 52 GiB）。MLX が推奨する上限は 51.8 GiB です。上限は `RAM − macOS の予約分` を超えません。Mac 全体の空きメモリの確認はこれまでどおり働きます（`MTPLX_M1_ENGINE_RAM_FRACTION=0.75` で元に戻る）。
- テスト：上限の割合をテストの共通設定で 0.75 に固定しました。M1 の上限、詰め替えの見積もり、直接の prefill の切り替えには、それぞれ専用のテストを足しました。

## v2.12.2-m1.1 での変更（2026-10-13）

prefill と decode を速くしました。どれも M1 系の Mac での既定で、M1 以外の Mac では今までどおりです（`MTPLX_M1_LONG_CONTEXT=0` ですべて止まります）。

### 前の版との比較（同じ時間帯に続けて計測）

M1 Max 64GB、`Youssofal/Qwen3.8-27B-MTPLX-Optimized-Speed-FP16`、turbo、depth 3、q8 の KV。

| | v2.12.2-m1 | v2.12.2-m1.1 | 比 |
|---|---|---|---|
| cold prefill 8.3K | 146 tok/s | **228** | 1.56 倍 |
| cold prefill 28.7K | 136 | **218** | 1.60 倍 |
| cold prefill 58K | 120 | **176** | 1.47 倍 |
| decode 2K（temperature 1.0、4 seed） | 27.7 tok/s | **31.6** | +14% |
| decode 32K（同） | 24.6 | **28.1** | +14% |

- greedy の要約（3 本）は、両方の版で書き出しが同じでした。
- decode の 1 ラウンドは、2K で 97.5 → 88.3 ms、32K で 105 → 97 ms です（draft と verify の合計）。tok/s には、draft の 8bit 化による受理率の違い（±3%）も入っています。
- 以前の別の計測（huihui 4bit、128K の会話）では、cold prefill が 1,350 → 927 秒でした。

### prefill

- **Neural Engine（ANE）との分担：** 各層の MLP の中間チャンネルの一部（10,240 チャンネル）を ANE で同時に計算します。ANE 側は int8 の活性値（512 ブロックの Hadamard 回転つき）× fp16 の重みです。Splash（Apache-2.0）の ANE の呼び出し方を MLX の上に作り直しました（`native_extensions/ane_ffn/`、`NOTICE`）。
  - prefill の塊を半分に分け、GPU と ANE が交互に休まず動くように重ねます。文脈が 32K までのときだけです。それより長いと GPU の見張り（watchdog）のエラーが出たので、半分ずつ順番に計算します。
  - 非公開の `AppleNeuralEngine.framework` を使います。macOS の更新で使えなくなったときや、ANE の呼び出しが失敗したときは、自動で GPU だけの計算に戻ります。止めるときは `MTPLX_ANE_PREFILL=0`。
  - 品質：greedy で 18 問中 11 問が完全一致でした。KV を q8 と fp16 で切り替えたときの変化と同じくらいです。70 分の連続運転でエラーは出ませんでした。
- **過去の KV に対する attention を metal-flash-attention で：** native 拡張にしました（`native_extensions/mfa_attn/`）。1 層あたり 1.38〜1.51 倍で、新しいトークンが 256 以上のときだけ使います。止めるときは `MTPLX_MFA_PREFILL=0`。
- **q8 の KV を層ごとに 1 回 fp16 に戻してから attention**（`MTPLX_KV_QUANT_PREFILL_DEQUANT=0` で止まる）と、**prefill の線形層を fp16 GEMM で**（ビット単位で同じ結果、`MTPLX_PREFILL_DEQUANT_GEMM=0`）。
- ANE を使うときは、prefill の塊の大きさを 4096 にします（自動のとき）。

### decode

- **verify の attention を 8 simdgroup で**（16K 以上、`MTPLX_GQA_MMA_NSG=4` で元に戻る）と、**MTP の層（fp16）を読み込み時に 8bit に**（`MTPLX_MTP_QUANT_BITS=0` で fp16 のまま）。
- **decode の間だけ、MLX のコマンドバッファの上限を 150 ops / 1,000 MB に**（prefill は MLX の既定のまま。`MTPLX_DECODE_CB_LIMITS=0`）。
- **ホストと GPU の往復を減らしました。** どれも出力は変わりません（同じ seed でビット単位で同じ）。
  - 受理の判定に使う確率を、1 位置ずつではなくまとめて 1 回で読みます（`MTPLX_M1_BATCH_TARGET_DEFAULT=0` で元に戻る）。
  - 12K を超える文脈で、16 層の KV の位置を 1 層ずつ読んでいたのを 1 回にまとめました（`MTPLX_PAGED_OFFSETS_MAX_CONTEXT`）。
  - **draft を GPU 上で 3 段続けて作る chain を既定にしました**（`MTPLX_QWEN4_SAMPLED_DRAFT_CHAIN=0` で 1 段ずつ）。以前は長い文脈で遅くなっていました（段ごとに MTP の KV を丸ごとコピーしていたため）。KV をその場で書き込む命令を native 拡張に追加して直しました（`MTPLX_MTP_INPLACE_KV=0`）。32K で 1 ラウンド −2.3%、110K で −1.7%。
- 3 つを合わせて、32K で 1 ラウンドが約 100 → 95 ms です。
- verify を draft の直後に積む切り替え（`MTPLX_CHAIN_EARLY_VERIFY=1`）も入れましたが、速くならなかったので既定は off です。

### その他

- dense の 4bit・8bit のモデル（Qwen3.8-27B など）は、M1 では turbo の profile を既定にしました（`MTPLX_M1_TURBO_DEFAULT=0` で元に戻る）。MoE はこれまでどおり sustained です。
- ネイティブ拡張は、利用者の環境でビルドが必要です（`scripts/build-m1-native-extensions.sh`、1 分ほど）。ビルドしなくても動きますが、ANE、metal-flash-attention、draft の chain は使われません。手順は USAGE を見てください。
- テスト：本家との差分によるテストの失敗のほか、M1 の既定値を前提にしていないテストがいくつか落ちます（`MTPLX_M1_LONG_CONTEXT=0` で通るものがほとんど）。

## v2.12.2-m1 での変更（2026-10-04）

### 本家 2.12.2 への追従

本家の v2.12.1 と v2.12.2 を取り込みました。
主な中身は、メモリガード（すべての要求の必要メモリを見積もり、足りなければスワップに入る前に 507 で断る）、SSD キャッシュとセッションバンクの改良、ツール呼び出しやストリームの修正などです（本家の CHANGELOG）。
m1.3 で直した「長い生成が約 1.65 万トークンで止まる不具合」は、本家も #526 として別の方法で直しました。
本家の方法（書き込む前に KV を広げ、メモリが足りなければ断る）に置き換え、M1 で使う q8 の「pages」形式の KV でも正しく広がるようにしました。

- 本家 2.12.2 との差は、この版の M1 向けのコードと、下の修正です。
- m1.3 との比較（M1 Max 64GB、Qwen3.8-27B、q8 の KV、greedy、3 ターンの会話）：生成文は 2K / 32K / 128K の 9 ターンすべてで同一でした。最初のプリフィルは 2〜3% 速く（128K で 1492 秒 → 1450 秒）、2 ターン目以降の応答開始は 0.1〜0.15 秒速く、decode は ±1% 以内でした。

### M1 の処理に合わせたメモリの見積もり

本家のメモリガードの見積もりは、本家の処理での実測にもとづいています。
M1 のこの版は処理が違うので、実測に合わせて直しました。

- **プリフィルの作業領域：** この版は M1 でプリフィルを MMA カーネルで行い、スコアの行列を作りません。2,048 行のチャンクで、見積もり 3.15 GB に対し実測は約 2.05 GB でした。M1 では本家の見積もりの 70% にしました（`MTPLX_M1_MMA_PREFILL_SCRATCH_FRACTION`、1 で本家と同じ）。
- **q8 の保存状態からの復元：** この版は q8 の保存状態を、fp16 に戻さずに q8 のページへ直接戻します。本家の見積もりは fp16 に戻してから詰め替える処理として数えていて、11.2 万トークンの会話に 19 トークンを足すだけの要求を 12.99 GB と見積もって断っていました。直した見積もりは 8.84 GB で、実測（11 万トークンの会話に 20 トークンの続き）は 7.38 GB でした。

### エージェントでの長い会話の修正（本家にもある不具合）

omp で思考オン（xhigh）の作業を続けたときに見つかった不具合です。
どれも M1 に限りません。

- **長い思考のあとで会話のキャッシュが外れる：** サーバーは、プロンプトの 25% 以上が前の会話と一致するときに同じ会話とみなします。思考が長いと（7 万トークン以上）、思考の序盤にあるトークンの区切りの違い（同じ文字列で、区切りだけが違う）が 25% を割り、別の会話と判定されて、思考の全体（約 7.8 万トークン）を読み直していました。分かれ目が前のターンで生成した部分の中にあり、同じ文字列に戻るときは、同じ会話とみなすようにしました。
- **ツール呼び出しの引数の空白：** サーバーが引数の値の前後の空白をすべて削っていました。書き込むファイルの末尾の改行や 1 行目の字下げが消え、さらにクライアントが送り返した履歴が生成と 1 文字違うため、会話の保存が見送られて、次の呼び出しで直前の思考（7.4 万トークン）を読み直していました。Qwen の書式で枠になる改行 1 つずつだけを除くようにしました（複数行の値はそのまま、1 行の値は従来どおり前後を削る）。
- **生成の途中で KV を広げられないとき：** 27B の KV はデコード中に広げますが、メモリが足りずに断られると、要求全体が 507 になり、それまでに書いた回答も失われていました。各ラウンドの手前で次のラウンドの分を確保し、断られたらその時点で止めて回答を残すようにしました（`finish_reason: length` と `memory_stop`）。
- **大きなキャッシュ外れの記録：** 1.6 万トークン以上のプロンプトで半分以上を読み直したとき、その理由（会話の判定、保存状態の一覧、直近の削除）をサーバーのログに 1 行で出します。

これらを入れた版で、omp の京都庭園の課題（思考 7.4 万トークン、12 回の呼び出し）が最後まで動きました。

## m1.3 での変更（2026-10-01）

- **長い生成が約 1.65 万トークンで止まる不具合を修正しました。** 本家にも同じ不具合があり、M1 に限らない修正です。
  - サーバーは生成用の KV キャッシュを最初に最大 16,384 トークン分だけ確保し、足りなくなったら増やす設計です。ところが compiled verify が使う形の KV キャッシュには容量を増やす処理がなく、確保した分を使い切ると容量の外に書き込んで値が壊れ、出力が NaN になってエラーで止まっていました。
  - thinking オンで長く考えさせると必ず起きていました（Qwen3.8-27B、xhigh で約 16,530 トークン目）。compiled verify の文脈の上限を下げても直らず、最初から全量を確保する設定（`MTPLX_DYNAMIC_PAGED_KV_MAX_INITIAL_NEW_TOKENS=unlimited`）では起きないことで原因を確定しました。
  - 修正：compiled verify の KV キャッシュにも容量を増やす処理を足し、足りなくなる前に増やすようにしました（1.5 倍か必要量の大きいほう）。17,500 トークンの再現手順と、thinking オンで最大 5.7 万トークンを生成する課題がすべて最後まで動き、速度は変わりませんでした。
  - 修正前の版での回避策は `MTPLX_DYNAMIC_PAGED_KV_MAX_INITIAL_NEW_TOKENS=unlimited` です（要求された生成量の KV を最初に確保するので、メモリを少し多く使います）。

- 「本家で同じ設定にできるか」が「できる」の項目は、本家 2.12.0 でも環境変数で同じ状態にできます。これらをすべて本家に与えた計測（「upstream + env」、#9 を除く）を公開ベンチに載せています。本家では 2K〜8K で +15% 前後、32K で +9% ですが、64K 以上では context-copy を切った分だけかえって遅くなりました（-8〜10%）。

- その他：Flash-Next など QSA attention のモデルで、#1 の draft 用の差し替えが本体の全層に及んでいた不具合を修正（27B は変化なし）。

## 総合ベンチマーク結果

- **測定環境：** M1 Max 64GB、Qwen3.8-27B、8-bit KV、greedy デコード、3 ターン会話、各ターン最大 256 トークン（[apple-silicon-llm-bench](https://github.com/shunya1810/apple-silicon-llm-bench)）
- **比較対象：** 本家コミット `1de2b1c`（v2.12.0 ＋ README 更新 1 コミット）。起動オプションは両者で同一で、違いは読み込むコード（`PYTHONPATH`）だけです。「本家 + env」は、同じ本家のコードに上表の「できる」の環境変数をすべて与えたものです。
- **計測日：** 本家と本家 + env は 2026-09-29 に同じセッションで交互に計測しました。本ビルド（タグ `v2.12.0-m1.2`）は 2026-09-30 に同じ計画で単独で計測しました（事前に 2K の確認でマシンの状態が同じことを確かめています）。
- decode は 3 ターンの平均（各ターンは 2 ラウンドの中央値。128K は 1 回）です。

| コンテキスト長 | 本家 decode | 本家 + env decode | 本ビルド decode | 本家 3 ターン総所要時間 | 本ビルド 3 ターン総所要時間 |
|---|---|---|---|---|---|
| **2K** | 23.6 tok/s | 27.2 tok/s | **29.3 tok/s** | 41.8 秒 | **36.0 秒** |
| **32K** | 14.0 tok/s | 15.3 tok/s | **25.5 tok/s** | 5.0 分 | **4.6 分** |
| **64K** | 8.7 tok/s | 7.8 tok/s | **23.4 tok/s** | 11.3 分 | **10.1 分** |
| **128K** | 5.0 tok/s | 4.6 tok/s | **19.0 tok/s** | 30.6 分 | **24.9 分** |

- `v2.12.0-m1`（2026-09-29 に本家と同じセッションで計測）は、decode が 31.8 / 27.0 / 24.3 / 19.6 tok/s、3 ターン総所要時間が 35.2 秒 / 4.7 分 / 10.9 分 / 25.3 分でした。m1.2 は decode が 3〜9% 低い代わりに、prompt の読み込みが速くなっています（「m1.1 での変更」）。
- サンプリング（temperature 1.0、top-p 0.95、top-k 20、最大 512 トークン）では、本ビルドが 2K / 32K / 64K で 27.5 / 25.2 / 23.8 tok/s、本家が 23.2 / 14.2 / 8.9 tok/s、本家 + env が 26.4 / 14.2 / 8.2 tok/s、Splash 1.1.0-m1 が 32.7 / 25.8 / 22.0 tok/s でした。
- Splash 1.1.0-m1 との比較：decode は 64K まで Splash が速い（2K〜8K で 13%、32K〜64K で 3〜6%。128K は本ビルドが 2% 速い）一方、3 ターン総所要時間は本ビルドが 2K〜128K で 5〜15% 短いです。短いプロンプト・推論ありの条件では、Splash の decode が 29% 速く、1 トークンあたりのエネルギーも約 3 分の 2 です。

> **読み方の注意：**
> - 総所要時間の差が decode ほど大きくないのは、1 ターン目のコールド prefill（64K で約 10 分）が時間の大半を占めるためです。本ビルドの prefill は 2K〜8K で本家と同じ、32K で 2.5% 遅く、64K で 4%、128K で 14% 速いです。
> - 各ターンの生成が 256 トークンと短い条件です。生成が長い使い方では decode の差が大きく効きます。
> - ピークメモリは本ビルドの方が少ないですが（128K で 43.5 GB 対 52.4 GB）、Splash（22〜26 GB）よりはかなり多いです。
