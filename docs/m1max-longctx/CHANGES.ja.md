# v2.12.0-m1 変更内容まとめ

- **ベースリポジトリ：** MTPLX 2.12.0（本家 `youssofal/MTPLX` の v2.12.0 ＋ README 更新 1 コミット）
- **対象：** タグ `v2.12.0-m1`（ブランチ `m1max-longctx`）
- **本家との差分：** コード 22 ファイル（約 2,400 行追加）、テストコード、各種ドキュメント（`docs/m1max-longctx/`）、起動・検証スクリプト

---

## 前提条件・適用範囲

- **M1 シリーズの Mac のみ適用：**
  チップ名が「Apple M1」で始まる環境（M1 / Pro / Max / Ultra）でのみ、本ブランチのチューニング（後述の既定値）が有効になります。M2 以降の Mac では本家 2.12.0 と同じ挙動になります。
- **最適化の一括無効化：**
  環境変数 `MTPLX_M1_LONG_CONTEXT=0` を指定して起動すると、M1 向けの既定値をすべて無効化し、本家の挙動に戻せます（#3 の不具合修正はコードの修正のため、そのまま残ります）。
- **検証済み環境：**
  動作確認は **M1 Max 64GB（macOS 26）＋ Qwen3.8-27B（FP16 版）** のみで実施しています。

## 変更点一覧

| # | 変更内容 | 変更の理由・背景 | 効果（M1 Max 64GB / 公開ベンチ） | リスク・留意点 | 無効化フラグ / オプション | 本家で同じ設定にできるか |
|---|---|---|---|---|---|---|
| **1** | **長文脈 Attention 用の専用カーネル**<br>（M1 行列演算命令 `simdgroup_matrix` を活用した verify / draft / prefill） | M1 環境では、本家の標準 Attention が長文脈時に大幅に減速するため | **decode 高速化の主因**。本家に #5〜#8 相当の環境変数を与えた「本家 + env」との差が、ほぼこのカーネル（と #3）の分です：decode 32K 15.3 → 27.0、64K 7.8 → 24.3、128K 4.6 → 19.6 tok/s（2026-09-29、同一セッション） | 浮動小数点演算の順序が変わるため、同一シードでも本家と生成文がわずかに変わる可能性がある（計算精度の妥当性はテストで検証済み）。 | `MTPLX_GQA_MMA=0`<br>`MTPLX_GQA_MMA_PREFILL=0` | できない（本ビルドのコード） |
| **2** | **長文脈時の自動 8-bit KV キャッシュ**<br>（131,072 トークン以上で自動切替。KV の量子化を何も指定しないときだけ） | 長文脈時のメモリ枯渇を防ぐため | 量子化を指定しない起動で 128K 以上のメモリを削減。公開ベンチは本家・本ビルドとも `--paged-kv-quantization q8` を明示しているため、ベンチの数値には効いていない | 8-bit 量子化により、ごくわずかな精度低下が生じる可能性がある。 | `--kv-quant off`（明示的に指定） | できる（`--paged-kv-quantization q8` を明示） |
| **3** | **セッションバンク（会話キャッシュ）の修正** | 量子化 paged KV や GDN 境界において、2 ターン目以降のキャッシュ再利用が正しく・速く働かない箇所があったため | 2 ターン目以降の応答開始（Time-to-First-Token）を短縮（128K で本家 3.5〜4.2 秒 → 2.2 秒。#1 との合算） | 低い | （自動適用） | できない（不具合修正） |
| **4** | **163,840 トークン超での prefill 分割サイズ縮小** | 256K の処理時にメモリが足りなくなるのを防ぐため | 64GB 機でも 256K の処理を完走可能に（公開ベンチの 128K 以下には効かない） | 低い（当該長さの prefill 時間がわずかに増加） | `MTPLX_PREFILL_CHUNK_SIZE_LONG_CONTEXT` で変更可能 | できない |
| **5** | **Context-copy ドラフトの既定無効化** | M1 環境では Context-copy のブロック検証が通常の MTP ラウンドの約 3 倍かかり、会話の 2〜3 ターン目では得より損が大きいため | decode（3 ターン平均）+1〜12%（`16751dc` → `40b6113`、計測日は別） | なし（本家の機能を既定で切るのみ） | `MTPLX_CONTEXT_COPY=1` で有効化 | できる（`MTPLX_CONTEXT_COPY=0`） |
| **6** | **メモリ既定値の削減**<br>（MLX バッファキャッシュ 1 GiB、保存状態数を 1 会話あたり 2 件に制限、prefill の MMA を最初の chunk から） | 64GB 機でのスワップ発生を防ぐため | 32K〜128K 時のピークメモリ使用量を **3.4〜6.4 GB 削減**（速度は同等） | なし | `MTPLX_M1_LONG_CONTEXT=0` | 一部できる（`MTPLX_MLX_CACHE_LIMIT=1G`、`MTPLX_SESSION_BANK_PER_SESSION_MAX_ENTRIES=2`。MMA prefill は #1 のコード） |
| **7** | **小型 GDN / Attention 射影の結合計算** | M1 では小さな行列演算のオーバーヘッドが大きいため | decode 速度が **+1.6〜2.7%** 向上 | 低い（浮動小数点順序の変化により、生成文がわずかに変わる場合あり） | `MTPLX_FUSE_PROJ=0` | できる（`MTPLX_FUSE_PROJ=gdn,attn`） |
| **8** | **ドラフト出力層の語彙プルーニング**<br>（FR-Spec：日本語トークンを含む頻出 10.4 万語に絞り込み） | ドラフト処理のたびに語彙層の重み 715 MB を読み込んでいたため | decode 速度が **+4〜7%**（日本語：+2〜6%）向上 | greedy では出力は同一。サンプリング時も出力の確率分布は変わらない（ドラフトは候補を出すだけで、採否はメインモデルが判定するため）。 | `MTPLX_FRSPEC_DRAFT=0` | 英語・コードはできる（`MTPLX_FRSPEC_DRAFT=1 MTPLX_FRSPEC_LEGACY=1 MTPLX_FRSPEC_VOCAB=builtin:qwen38-code-64k`）。本家の 64K 語彙は日本語を 78〜84% しか覆わず、日本語 decode が約 25% 落ちる |
| **9** | **Metal コマンドバッファの拡大**（最大 150 ops / 1,000 MB）＋ **prefill の 4 層ごとの確定** | バッファ境界での GPU アイドル（1 ラウンドあたり約 13% の待機時間）を削減するため | decode 速度が **+4〜11%** 向上（公開ベンチ `bba1b7b` → `0cd2a73`：+6.3〜9.6%） | 生成文は同一。初回読み込み（prefill）が 2K〜32K で 1〜5% 遅くなる（2026-09-29 の公開ベンチ）。 | `MLX_MAX_OPS_PER_BUFFER`<br>`MLX_MAX_MB_PER_BUFFER` を明示指定 | 勧めない（2 変数は MLX 本体の設定なので本家にも与えられるが、4 層ごとの確定なしではピークメモリが 12〜15 GB 増え、128K でメモリ不足になった。decode は変わらない） |

- 効果の数値は、公開ベンチで版ごとに測り直した差分です。#5 以降は計測日が別のため、数 % は日による揺れを含みます。
- 「本家で同じ設定にできるか」が「できる」の項目は、本家 2.12.0 でも環境変数で同じ状態にできます。これらをすべて本家に与えた計測（「upstream + env」、#9 を除く）を公開ベンチに載せています。本家では 2K〜8K で +15% 前後、32K で +9% ですが、64K 以上では context-copy を切った分だけかえって遅くなりました（-8〜10%）。

- その他：Flash-Next など QSA attention のモデルで、#1 の draft 用の差し替えが本体の全層に及んでいた不具合を修正（27B は変化なし）。

## 総合ベンチマーク結果

- **測定環境：** M1 Max 64GB、Qwen3.8-27B、8-bit KV、greedy デコード、3 ターン会話、各ターン最大 256 トークン（[apple-silicon-llm-bench](https://github.com/shunya1810/apple-silicon-llm-bench)）
- **比較対象：** 本家コミット `1de2b1c`（v2.12.0 ＋ README 更新 1 コミット）。起動オプションは両者で同一で、違いは読み込むコード（`PYTHONPATH`）だけです。「本家 + env」は、同じ本家のコードに上表の「できる」の環境変数をすべて与えたものです。
- **計測日：** 3 つとも 2026-09-29 に同じセッションで交互に計測しました（本ビルドはタグ `v2.12.0-m1`）。
- decode は 3 ターンの平均（各ターンは 2 ラウンドの中央値。128K は 1 回）です。

| コンテキスト長 | 本家 decode | 本家 + env decode | 本ビルド decode | 本家 3 ターン総所要時間 | 本ビルド 3 ターン総所要時間 |
|---|---|---|---|---|---|
| **2K** | 23.6 tok/s | 27.2 tok/s | **31.8 tok/s** | 41.8 秒 | **35.2 秒** |
| **32K** | 14.0 tok/s | 15.3 tok/s | **27.0 tok/s** | 5.0 分 | **4.7 分** |
| **64K** | 8.7 tok/s | 7.8 tok/s | **24.3 tok/s** | 11.3 分 | **10.9 分** |
| **128K** | 5.0 tok/s | 4.6 tok/s | **19.6 tok/s** | 30.6 分 | **25.3 分** |

- サンプリング（temperature 1.0、top-p 0.95、top-k 20、最大 512 トークン）では、本ビルドが 2K / 32K / 64K で 32.3 / 27.3 / 24.1 tok/s、本家が 23.2 / 14.2 / 8.9 tok/s でした（同じベンチの sampled の表）。
- 他のエンジンとの比較（Splash 1.1.0-m1 など）もベンチにあります。短い文脈（2K〜8K、greedy）では Splash 1.1.0-m1 が約 4% 速く、32K 以上では同等です。

> **読み方の注意：**
> - 総所要時間の差が decode ほど大きくないのは、1 ターン目のコールド prefill（64K で約 10 分）が両者ほぼ同じためです。本ビルドの prefill は 2K〜32K で本家より 1〜5% 遅く、128K では 12% 速いです。
> - ピークメモリは本ビルドの方が少ないですが（128K で 46 GB 対 52 GB）、Splash（22〜26 GB）よりはかなり多いです。
> - GPU 温度と消費電力は測っていません。

## この版について（免責事項）

1. **非公式ビルド：** MTPLX 公式プロジェクトとは無関係で、サポートや動作保証はありません。
2. **検証環境の限定：** 動作確認は M1 Max 64GB かつ Qwen3.8-27B のみです。他の M1 モデル、小容量メモリ機（16〜32GB）、他のモデルでの動作は未検証です。
3. **AI 支援による開発：** 変更コードは AI（Claude）の支援を受けて作成しました。
4. **アップストリーム追従：** 本ビルドは 2.12.0 をベースとしており、将来の本家アップデートへの追従は保証しません。
5. **元に戻す方法：** 不具合が生じた場合は、環境変数 `MTPLX_M1_LONG_CONTEXT=0` を指定するか、MTPLX アプリを通常どおり起動すれば、本家の挙動に戻せます。
